# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

FranVision is a real estate photography studio's internal tooling, being built module-by-module toward one Job → one client delivery page with photos, Feature Sheet, video, invoice/payment. **As of 2026-09-15, the target platform is a unified custom system built with Claude Code on top of Supabase — NOT Wix Studio/Velo.** This reverses the plan recorded in `FranVision_整体架构总览.md` (Wix-hosted platform, Wix CMS = business/payment state): a Wix Velo bug (`wix-secrets-backend.v2`'s `getSecretValue()` returning an unresolvable `FORBIDDEN`) triggered a step back that concluded Wix's visual-editing advantage only actually applies to Feature Sheet Builder and the delivery page — everything else on the roadmap (agent portal, admin/CRM, financials, staff RBAC, Job Generator integration) is standard functional UI better served by code + Supabase (Auth/RLS/Postgres). See `franvision-architecture-strategy-decision.md` for the full reasoning and decision, and `franvision-delivery-page-design-spec.md` for the delivery page's target visual design (based on a Zenfolio page Franky already uses, to be reproduced in custom code, not ported from Wix). `FranVision_整体架构总览.md` now records superseded decision background — where any of these three documents conflict, `franvision-architecture-strategy-decision.md` wins as the most recent.

There is no root build system (no root `package.json`) — each module below is independently run, tested, and (where applicable) deployed.

## Modules

Each module's own `CLAUDE.md` is the source of truth for how it works, its architecture, and its confirmed design decisions — the bullets below are only a one-line index plus how to run/test it. When you change a module in a way that makes its bullet here inaccurate, update the bullet in the same change (see the sync-discipline convention below).

- **`job-generator/`** — local Node tool: Job folder creation, pricing/commission, Dropbox sync, bilingual Delivery Email. See **`job-generator/CLAUDE.md`** for full detail (Supabase job server, Draft vs. Job model, Windows support status). Quick start: double-click `Job Generator.command`, or `cd job-generator && node server.js` → http://localhost:4173. Tests: `cd job-generator && npm test`.

- **`pricing/`** — the pricing calculation engine. **Single source of truth for pricing logic — never duplicate pricing rules elsewhere.** See **`pricing/CLAUDE.md`** for full detail (config-only-editing rule, the advisor tool, ESM ports, confirmed-rules record). Tests: `node pricing/engine.test.js`.

- **`feature-sheet-builder/`** — client-facing self-serve tool for building a 2-page real estate Feature Sheet PDF. See **`feature-sheet-builder/CLAUDE.md`** for full detail (architecture, backends, the `fsb-v2` template system, Job-connected galleries, deploy). Quick start: `cd feature-sheet-builder && node server.js` → http://localhost:4180 (or double-click `Feature Sheet Builder.command`). Tests: `cd feature-sheet-builder && npm test`.

- **`photo-sync-worker/`** — standalone Cloudflare Worker mirroring Dropbox job photos/videos into the Feature Sheet Builder's Supabase project + Cloudflare Stream. **Needs the Workers Paid plan.** See **`photo-sync-worker/CLAUDE.md`** (plus `DESIGN.md`/`README.md` there) for full detail (pipeline, self-heal, thumbnail sourcing). - **`delivery-page/`** — the custom-code client delivery page, a standalone Cloudflare Worker serving `/<slug>/<jobId>` from the same Supabase project `photo-sync-worker` writes to. ## Cross-module conventions worth knowing before editing any module

- **This file stays an index, not a spec.** Feature descriptions, mechanism/architecture detail, and design rationale belong in each module's own `CLAUDE.md` (or a root-level design-decision doc for cross-module calls, e.g. `franvision-architecture-strategy-decision.md`) — not inlined here. This file is auto-loaded into every session regardless of task relevance, so it should only hold what's needed on nearly every task: orientation, cross-module rules, and pointers. A module bullet above going stale (wrong status, a moved/retired feature) is worse than no bullet, since nothing else will catch the drift — when a change makes one inaccurate, fix it in the same change, and prefer a short factual pointer ("see X for Y") over restating X's content, since a restatement drifts as X evolves and a bare pointer mostly can't.
- **Server-authoritative pricing**: a client (browser) always sends its current selection, and the server always recomputes the price from scratch before doing anything consequential (creating a job, unlocking a download) — never trust a client-computed total. Applies in `job-generator/server.js` and is the intended pattern for the future Wix Gallery/PaymentGate work too.
- **Zero-dependency-by-default philosophy**: `pricing/` and (until 2026-09-06) `job-generator/` had no npm dependencies at all — plain Node built-ins only, UMD modules loadable by both Node and a browser `<script>` tag. `job-generator/` broke this once, deliberately, to add the `dropbox` SDK (no reasonable way to drive Dropbox's chunked-upload API without it) — see `job-generator/CLAUDE.md`.
- **Real credentials never enter this repo.** `.gitignore` excludes every module's `.env`; each module that needs secrets ships a `.env.example` documenting the required keys with no real values.
- **One git worktree per concurrent line of work — never two sessions (or a session and a manual `git checkout`) sharing the same worktree directory at the same time.** A worktree directory only ever has ONE branch checked out; if a second session runs `git checkout`/`git switch` in that same directory, it silently swaps the files under whatever else is working there — found in real use (2026-09-11): two Claude Code sessions both working in `/Users/siyuan/Desktop/FranVision` meant one session's branch checkout silently replaced the other session's already-fixed files with an older, still-buggy version, without either session noticing until a diagnostic check caught it. Nothing was lost (git history is safe regardless), but it wasted real time and could easily have caused a regression to ship unnoticed. The project already uses `git worktree add <dir> <branch>` for exactly this (`FranVision`, `FranVision-main`, `FranVision-photo-sync-worker` are three worktrees off one `.git`) — extend the same pattern: before starting a new, separate line of work (a new feature, a second concurrent session), give it its own worktree directory (named to match its branch) rather than reusing a directory another session might still be using. Before trusting any assumption about "where the repo currently is," a session should itself verify with `git branch --show-current` / `git log --oneline -5` / `git status` rather than relying on stale context.

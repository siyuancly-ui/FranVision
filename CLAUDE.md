# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

FranVision is a real estate photography studio's internal tooling, being built module-by-module toward one Job → one client delivery page with photos, Feature Sheet, video, invoice/payment. **As of 2026-09-15, the target platform is a unified custom system built with Claude Code on top of Supabase — NOT Wix Studio/Velo.** This reverses the plan recorded in `FranVision_整体架构总览.md` (Wix-hosted platform, Wix CMS = business/payment state): a Wix Velo bug (`wix-secrets-backend.v2`'s `getSecretValue()` returning an unresolvable `FORBIDDEN`) triggered a step back that concluded Wix's visual-editing advantage only actually applies to Feature Sheet Builder and the delivery page — everything else on the roadmap (agent portal, admin/CRM, financials, staff RBAC, Job Generator integration) is standard functional UI better served by code + Supabase (Auth/RLS/Postgres). See `franvision-architecture-strategy-decision.md` for the full reasoning and decision, and `franvision-delivery-page-design-spec.md` for the delivery page's target visual design (based on a Zenfolio page Franky already uses, to be reproduced in custom code, not ported from Wix). `FranVision_整体架构总览.md` now records superseded decision background — where any of these three documents conflict, `franvision-architecture-strategy-decision.md` wins as the most recent.

There is no root build system (no root `package.json`) — each module below is independently run, tested, and (where applicable) deployed.

## Modules

- **`job-generator/`** — local Node tool that creates a Job's folder structure, computes pricing/commission, syncs files with Dropbox, and generates a bilingual Delivery Email `.txt` (interim stand-in for the eventual client delivery page, with Dropbox download links auto-filled per deliverable ordered). See **`job-generator/CLAUDE.md`** for full detail. Quick start: double-click `Job Generator.command`, or `cd job-generator && node server.js` → http://localhost:4173. macOS only for now — see `job-generator/CLAUDE.md`'s Known limitations for the state of Windows support. Tests: `cd job-generator && npm test` (or `node run-tests.js`) — plain `node --test`-free, hand-rolled runner per file, no test framework, cross-platform.

- **`pricing/`** — the pricing calculation engine (`engine.js` + `pricing-config.js`), zero dependencies, UMD (works via `require()` in Node and a plain `<script>` tag in the browser). This is the **single source of truth for pricing logic** — `job-generator/pricing-adapter.js` wraps it directly rather than reimplementing anything; do not duplicate pricing rules elsewhere. `pricing-config.js` is the only file that should need editing when prices/packages change — never hardcode prices in `engine.js` or any UI. Manual interactive tester: open `pricing/tester.html` directly in a browser. Tests: `node pricing/engine.test.js`. `engine.esm.js`/`pricingconfig.esm.js` at the repo root are hand-kept ES Module ports of the same two files (for Wix Velo, which requires ESM) — logic must stay identical to the UMD originals; see the files' own header comments before editing either version.

- **`feature-sheet-builder/`** — client-facing self-serve tool for building a 2-page real estate Feature Sheet PDF from a fixed template. See **`feature-sheet-builder/CLAUDE.md`** for full detail (architecture, the two backends, the `fsb-v2` template system, deploy). Quick start: `cd feature-sheet-builder && node server.js` → http://localhost:4180 (or double-click `Feature Sheet Builder.command`); the browser talks straight to Supabase unless `public/js/config.js` is blank or the URL has `?local=1`. A sheet can be connected to a Job (admin types the Job ID inside it) to use that Job's Dropbox-synced gallery as its photo library, read-only (see its CLAUDE.md §4). Tests: `cd feature-sheet-builder && npm test`. Deploys to Cloudflare Workers (assets-only) via `wrangler.jsonc` at the repo root — either through the Cloudflare dashboard's auto-build on push to `main`, or manually via `bash deploy.sh` from the repo root. `feature-sheet-builder/README.md` / `NOTES.md` cover the older `jason-fs-v1` template and the Supabase SQL schema.

- **`photo-sync-worker/`** — a standalone Cloudflare Worker (`franvision-photo-sync`, **needs the Workers Paid plan** for Queues) that mirrors compressed thumbnails of Dropbox job-folder photos into the Feature Sheet Builder's Supabase project (`projects` table + `photos` bucket, plus a new `photo_sync_state` table and two atomic RPCs), and writes a larger `w2048h1536` delivery render back into Dropbox at `<job>/MLS for download/`. Dropbox webhook + a 2-min reconciliation cron → Cloudflare Queue → per-job thumbnail/upsert, with a delete→`pending_review`→same-name-re-upload self-heal. Thumbnails are produced by **Dropbox's own thumbnail API**, not Cloudflare Image Resizing. Also mirrors job videos (`Video`/`VLOG` folders) into **Cloudflare Stream** (async "copy from URL" ingest, polled to completion by the same 2-min cron), writing playback info into the same Supabase project's `projects.data.videos[]`. Reuses the Job Generator's Dropbox app + the `jobId` PropertyGroupTemplate; secrets via `wrangler secret put`, never a file. See **`photo-sync-worker/CLAUDE.md`** (plus `DESIGN.md` / `README.md` there). Tests: `cd photo-sync-worker && npm test` (`node --test`, no network). Deployed, acceptance-tested, and merged to `main`.

- **`delivery-page/`** — the custom-code delivery page itself (started 2026-09-15, first module built under the pivot below), a standalone Cloudflare Worker (`franvision-delivery-page`) serving `/delivery/<jobId>` from the same Supabase project `photo-sync-worker` writes to. See **`delivery-page/CLAUDE.md`**. Tests: `cd delivery-page && npm test` (`node --test`, no network). Scaffolded and unit-tested; not yet deployed or verified against a real Job — see its CLAUDE.md's Known limitations (no hero/closing photo curation, no annotated-aerial-photo data source, no map provider chosen).

- **Wix/Velo integration is discontinued** (2026-09-15, see `franvision-architecture-strategy-decision.md`). A Router-based delivery page skeleton was built in a separate repo (`siyuancly-ui/FranVision-WIX`) but hit an unresolvable Velo platform bug; the delivery page is being rebuilt in custom code instead — see `delivery-page/` above. Do not resume Wix Velo work on this basis without re-reading that decision doc.

## Cross-module conventions worth knowing before editing any module

- **Server-authoritative pricing**: a client (browser) always sends its current selection, and the server always recomputes the price from scratch before doing anything consequential (creating a job, unlocking a download) — never trust a client-computed total. Applies in `job-generator/server.js` and is the intended pattern for the future Wix Gallery/PaymentGate work too.
- **Zero-dependency-by-default philosophy**: `pricing/` and (until 2026-09-06) `job-generator/` had no npm dependencies at all — plain Node built-ins only, UMD modules loadable by both Node and a browser `<script>` tag. `job-generator/` broke this once, deliberately, to add the `dropbox` SDK (no reasonable way to drive Dropbox's chunked-upload API without it) — see `job-generator/CLAUDE.md`.
- **Real credentials never enter this repo.** `.gitignore` excludes every module's `.env`; each module that needs secrets ships a `.env.example` documenting the required keys with no real values.
- **One git worktree per concurrent line of work — never two sessions (or a session and a manual `git checkout`) sharing the same worktree directory at the same time.** A worktree directory only ever has ONE branch checked out; if a second session runs `git checkout`/`git switch` in that same directory, it silently swaps the files under whatever else is working there — found in real use (2026-09-11): two Claude Code sessions both working in `/Users/siyuan/Desktop/FranVision` meant one session's branch checkout silently replaced the other session's already-fixed files with an older, still-buggy version, without either session noticing until a diagnostic check caught it. Nothing was lost (git history is safe regardless), but it wasted real time and could easily have caused a regression to ship unnoticed. The project already uses `git worktree add <dir> <branch>` for exactly this (`FranVision`, `FranVision-main`, `FranVision-photo-sync-worker` are three worktrees off one `.git`) — extend the same pattern: before starting a new, separate line of work (a new feature, a second concurrent session), give it its own worktree directory (named to match its branch) rather than reusing a directory another session might still be using. Before trusting any assumption about "where the repo currently is," a session should itself verify with `git branch --show-current` / `git log --oneline -5` / `git status` rather than relying on stale context.

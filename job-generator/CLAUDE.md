# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this directory (`job-generator/`). See the repo-root `CLAUDE.md` for how this module fits into the rest of FranVision.

## What this is

A local, double-click-to-run tool for a real estate photography studio. Given a client/property/shoot-date/service selection, it:
1. Computes pricing via `pricing/engine.js` + `pricing/pricing-config.js` (never reimplemented here — see `pricing-adapter.js`)
2. Computes a photographer commission via an independent rate engine (never touches pricing)
3. Generates a unique Job ID (`FVS-YYYYMMDD-XXX`, increments per day)
4. Creates a standardized local folder structure
5. Writes `Job Info.txt` (human-readable) and `job.json` (machine-readable, integer cents)
6. Optionally generates a `.ics` calendar file for the shoot from an optional Shoot Time + free-text notes + images (e.g. a lockbox code or a screenshot of the agent's instructions)
7. Optionally mirrors the folder skeleton + files to Dropbox, and can later push/pull local ↔ Dropbox two-way for an existing job
8. Generates two **Delivery Email** `.txt` files (Chinese + English) with Dropbox shared links for whichever deliverables were ordered auto-filled in — an interim, transitional stand-in for the eventual client delivery page (see root `CLAUDE.md`'s long-term vision). See `delivery-email.js`.

Before a Job ID is assigned, the whole form can be saved as a **Draft** — **since 2026-09-19 a Draft creates no folder at all**: it lives on the job server, plus one calendar `.ics` dropped into the Job Root Folder when a Shoot Time is set (see the "Save as Draft creates NO folder" bullet below, which supersedes the 2026-09-13 Draft/Job unification model where a Draft was a real folder/`job.json`/Dropbox mirror with `jobId: null`). Clicking Create Job later creates the folders and assigns the real ID.

job-generator is expected to eventually be ported into the Wix/Velo backend (see root `CLAUDE.md`) — nothing here is that port yet, but keep that in mind when choosing a data shape for anything new (e.g. `form-state.js`'s sidecar record is a clean, filesystem-agnostic JSON object for exactly this reason).

## Running it

```bash
cd job-generator
npm install          # only needed once, or after pulling changes to package.json
node server.js        # -> http://localhost:4173
```

Or double-click `Job Generator.command` (macOS) at the repo root. Both just `cd` into `job-generator/` and `node server.js`. The code itself is cross-platform Node; the only OS-specific piece is `server.js#pickFolderNative()` (the "Browse…" folder dialog) — AppleScript on macOS, with a graceful "just type the path" fallback anywhere else. **A Windows launcher (`Job Generator.bat`) + a PowerShell `FolderBrowserDialog` branch in `pickFolderNative()` were built and tested on macOS (2026-09-11) but are deliberately not on `main`** — Windows support has died from being untested-then-stale before (a prior `windows-support` branch, abandoned 2026-09-08), and this codebase is still developed and verified on macOS only; see the `job-generator-delivery-email-followup`/`job-generator-next-2` line if picking Windows support back up. See Known limitations below.

One real correctness bug WAS found and fixed via that Windows testing, even though the Windows launcher itself isn't merged (2026-09-11): `server.js` used to derive `componentFolders` by running `folder-builder.js`'s own output through `path.join()`/`path.relative()` (to create the local folders, then convert back) instead of calling `folderBuilder.getComponentFolders(order)` directly — `path.join`/`path.relative` use the HOST OS's native separator (`\` on Windows), so on Windows `"0 RAW/1 Raws"` came out as `"0 RAW\1 Raws"`, which `dropbox-sync.js#expandFolderPaths()` (splits on `/` only) never split — Dropbox got one oddly-named folder with a literal backslash in it instead of a proper `"0 RAW"` parent, so `"0 RAW"` itself never appeared. This never manifested on macOS (POSIX paths already use `/`, so the round-trip was a no-op there) — the fix is a pure, zero-behavior-change-on-macOS correctness improvement, kept regardless of the Windows-launcher decision above. **Be wary of any other code that derives a folder-list string via `path.join`/`path.relative`/`path.sep` instead of reading it straight from `folder-builder.js#getComponentFolders()`** — that's the general shape of this bug class.

## Tests

No test framework — each `*.test.js` file is a self-contained script using plain Node `assert` + a hand-rolled pass/fail runner (`node <name>.test.js`). Run the whole suite with `npm test` (cross-platform, via `run-tests.js`), or by hand:

```bash
cd job-generator
for f in *.test.js; do node "$f" || echo "FAILED: $f"; done   # macOS/Linux
node run-tests.js                                              # any OS
```

As of 2026-09-19 this is 337 tests across 16 files, all passing. Dropbox-touching modules (`dropbox-sync.js`, `file-sync.js`) never hit the real API in tests — every async orchestrator function accepts an injectable `client` (and `downloadImpl`/`thresholds` where relevant) so tests supply a fake Dropbox client object instead. **When verifying Dropbox behavior beyond what the fake-client tests cover, you are testing against the studio's real, live production Dropbox account** (confirmed directly — hundreds of real client job folders live at the account root) — always use an obviously-fake job name, and always clean up (`filesDeleteV2`) whatever you create before finishing.

## Architecture: module map

Every module below is plain Node (`module.exports`), most also loadable as a browser `<script>` (UMD pattern, `window.X`) for the ones the client-side UI needs directly — those are whitelisted in `server.js`'s `SHARED_FILES` map and served at `/shared/*.js`.

| File | Role |
|---|---|
| `sanitize.js` | Cross-platform-safe folder/file names; `buildJobFolderName()` — the one place the top-level job folder name is constructed |
| `validate.js` | `isValidShootDate()` — strict `yyyy/mm/dd`, real calendar validation |
| `id-generator.js` | `FVS-YYYYMMDD-XXX` (`getNextJobId`), source of truth is scanning each job folder's `job.json` (not folder names) for today's max sequence; also `findExistingJob(root, folderName)` — the "is this an UPDATE of a job that already exists?" check; and `getNextJobIdChecked` (async, cross-machine collision guard — see the 2026-09-15 decision below) |
| `folder-builder.js` | `getComponentFolders(order)` (pure) + `createJobFolders()` (fs) — the **single source of truth** for "what folders a job needs"; both local creation and the Dropbox mirror consume its output. Also `diffComponentFolders(newOrder, oldOrder)` + `folderHasRealFiles()` for the update path |
| `pricing-adapter.js` | Thin wrapper around `pricing/engine.js` + `pricing/pricing-config.js` — never reimplements pricing |
| `commission-config.js` / `commission-engine.js` | Photographer commission — **entirely independent from pricing**, no shared code or state |
| `job-files.js` | Writes `Job Info.txt` + `job.json`; owns `computePendingConfirmation()` |
| `calendar-file.js` | Optional `.ics` calendar file for the shoot (Shoot Time + free-text notes + images), written as `<job folder>/Shoot Schedule.ics` with image LINKS in the event DESCRIPTION (2026-09-21; no base64 ATTACH any more; old ATTACH files are still readable) |
| `form-state.js` | Per-job sidecar (`.form-state.json`, local-only) carrying the few form fields `job.json` doesn't (shootTime, notes, chosenCandidateIndex, commission checkboxes) — so a Draft or Recent Job reloads fully into the form |
| `job-list.js` | Drafts panel + Recent Jobs panel listings — scans the Job Root Folder's `job.json` files, split by whether `jobId` is `null` (Draft) or a real string not yet marked Complete (Recent Job — permanent, no time window, since 2026-09-22; also owns `markJobCompleted()`) |
| `config-store.js` | Persists the default Job Root Folder to `.config.json` |
| `dropbox-sync.js` | Best-effort: `syncJobFolderToDropbox` creates the empty Dropbox folder skeleton + tags it with a hidden `jobId` property; `updateJobFoldersOnDropbox` adds newly-needed folders and prunes no-longer-needed EMPTY ones on an update; `ensureMlsForDownloadFolder` + `createSharedLink` back `delivery-email.js` (see below) |
| `file-sync.js` | Two-way Push/Pull of actual file *contents* for an **existing** job, any time after creation, as many times as needed. Internal naming (functions, API routes, `direction` field) stays "push"/"pull" throughout the codebase; only the **UI-facing text** was renamed 2026-09-11 — buttons read "Sync to Dropbox" / "Sync to Local" and the progress/hint copy matches, because "Push/Pull" reads as git jargon to Franky (non-technical). Keep this distinction in mind: code you read still says push/pull, the screen says sync. |
| `delivery-email.js` + `delivery-email-template.zh.txt` / `.en.txt` | Generates the two Delivery Email `.txt` files at Create/Update Job time — see the "Delivery Email" decision below |
| `wave-backend.js` | Optional Wave invoicing (2026-09-23) — wraps the sibling `../wave-invoicing/` library (pure request builder + GraphQL client) with config (`WAVE_*` env vars + `wave-product-map.json`), a cached customer list (Wave has no server-side name search) for the picker, and `buildAndSubmitInvoice()` (create or patch a DRAFT invoice). See "Wave invoicing" below. |
| `server.js` | Node `http`, zero framework, wires all of the above into a small JSON API |
| `public/index.html` | The UI — plain JS, no framework, no build step |

All of `folder-builder.js`, `pricing-adapter.js`, and `commission-engine.js` are driven by the **same `order` shape** (`{propertyType, photography, addons}`) — this is deliberate: one selection model feeds folders, pricing, and commission defaults instead of three parallel ones.

## Confirmed design decisions (do not "fix" without re-reading this — several of these were tried the "obvious" way first and explicitly reverted)

- **Photographer Name is optional at job creation.** Client Name, Address, Shoot Date, Job Root Folder, and a valid service selection block the Create button; Photographer Name does not.
- **Virtual Staging folder creation is decoupled from its pricing qty.** Checking the box creates the folder immediately even at qty 0 (photo count often isn't known until after the shoot) — `folder-builder.js`'s rule is `!!addons.virtual_staging || stagingQty > 0`, not `stagingQty > 0` alone.
- **`pendingConfirmation`** (`job-files.js#computePendingConfirmation`) is the single mechanism for "allowed to be incomplete now, must be caught before invoicing" — currently covers: missing Photographer Name, unconfirmed Virtual Staging qty, and a failed/skipped Dropbox sync. Surfaced in `job.json`, `Job Info.txt`, and the UI's success panel. There is intentionally **no** separate "mark job complete" workflow yet.
- **Twilight and 3D Tour have no dedicated folder** (removed 2026-09-06) — Luxury tier still gets `0 RAW/4 Raw HDR`, `three_d_tour` is still a real priced pricing-config.js addon, neither gets a folder anymore.
- **`Local Report`** is an always-present, empty, top-level folder (added 2026-09-07), same treatment as `Revisions`.
- **`Home Report` was REMOVED from `getComponentFolders()`'s always-present list on 2026-09-10.** It was never a real distinct folder — it was a naming mistake made at v1: the original spec called for "本地报表" (= "Local Report") per the price sheet, but got typed in as "Home Report" instead. When `Local Report` was added on 2026-09-07 (correctly named this time), nobody noticed `Home Report` was the same thing under the wrong name, so both got generated on every job for a few days until Franky's Windows testing surfaced it. **There IS a real, separate "Home Report" service** — newly added, not yet wired into `pricing/pricing-config.js`. When that pricing work happens, it gets its own CONDITIONAL folder entry in `getComponentFolders()` (tied to that new service being selected) — do not restore it as unconditional, and do not build it before the pricing side exists. `file-sync.js`'s `KNOWN_COMPONENT_FOLDER_NAMES` safety set still lists `'Home Report'` deliberately (jobs created before this fix have a real `Home Report` subfolder on disk; the set's job is to catch someone pointing Push/Pull at a job's own subfolder, not to mirror `getComponentFolders()`'s current output).
- **Folder-name date has no leading zero** (`sanitize.js#formatDateForFolderName`, added 2026-09-08): `"2026.9.8 Address_Client"`, not `"2026.09.08 ..."` — matches the studio's existing real-folder naming habit. The Shoot Date **input field** still requires strict zero-padded `yyyy/mm/dd` (unrelated — that's for unambiguous validation, not display).
- **`job.json` and `Job Info.txt` are local-only, never synced to Dropbox** (`file-sync.js`'s `LOCAL_ONLY_FILENAMES`) — explicit requirement, found because they were initially reaching Dropbox incidentally via a later Push.
- **Photographer Commission**: config is keyed **per photographer** (`commission-config.js`), not a single shared rate + one exempt name — a future photographer can get their own rate table, not just an exempt flag. Franky is `{exempt: true}` in config, never a hardcoded name check in the engine. Video (Walkthrough and/or Vlog) always maps to ONE `$50` line item, never doubled. Defaults auto-derive from the order but the user can freely override every checkbox before Create Job.
- **Pricing Breakdown "Subtotal" row (fixed 2026-09-11) shows the ADJUSTED figure (`finalSubtotalCents`), not the raw line-items sum (`subtotalCents`).** `pricing/engine.js` itself was always correct — HST/Total are computed off `finalSubtotalCents` — this was a `public/index.html#renderTotals()` display bug: the row labeled "Subtotal" showed `subtotalCents` (pre-adjustment), so the number next to "Subtotal" didn't match what HST was actually taken from. Fixed by rendering `finalSubtotalCents` there instead (a no-op when there's no adjustment, since the two are then equal) and moving "Manual adjustment" to appear BEFORE "Subtotal" so the rows read correctly top-to-bottom. `job-files.js`'s `Job Info.txt` rendering was already numerically correct (`subtotalCents + manualAdjustmentCents`, same value as `finalSubtotalCents`) and was simplified to use `finalSubtotalCents` directly. **`pricing/engine.js` and `pricing-config.js` were NOT touched** — this was never a pricing-logic bug, only a job-generator display one.
- **Manual Adjustment has a second input mode (added 2026-09-11): set the exact pre-tax package price directly**, instead of figuring out a ± delta by hand (e.g. rounding off a number in a real negotiation). `#adjustment-override` in `public/index.html` — typing a dollar amount there computes the equivalent `manualAdjustmentCents` as `override − currentSelectedSubtotalCents()` and clears the `#manual-adjustment` field (and vice versa: typing in `#manual-adjustment` clears the override) — the two fields are two UI-level views of the SAME underlying `order.manualAdjustmentCents`, never combined/stacked. `pricing/engine.js`'s API is unchanged; only ever the resulting `manualAdjustmentCents` delta is sent to `/api/price`/`/api/create-job` or persisted in `job.json` — reopening a draft/existing job always restores it into the `#manual-adjustment` field, never `#adjustment-override`, since only the delta is ever recorded.
- **Dropbox sync is always best-effort and must never block local job creation.** `dropbox-sync.js` and `file-sync.js` are designed to never throw — every failure mode comes back as a result object (`{success:false, error, ...}`), never a rejected promise, and callers in `server.js` wrap the calls in try/catch anyway as a second layer.
- **File sync is two explicit directions (Push / Pull), never a single auto-merging action.** A file changed on both sides since the last confirmed sync is a **conflict** — left untouched on both sides and reported, never auto-resolved (not "newer timestamp wins"). Deletions mirror to the other side too, unless the side being deleted *from* also changed since the last sync, which is likewise a conflict rather than a silent delete. This rests on a per-job manifest (`.dropbox-sync-manifest.json`, lives inside the job folder, itself excluded from syncing) recording the **last confirmed state on both sides** per file (`{local: {size, mtimeMs}, dropbox: {rev, size}}`) — the decision logic (`planPush`/`planPull`) is pure and fully unit-tested without any Dropbox client.
- **Push/Pull restores a file the manifest thinks the OTHER side has but doesn't, fixed 2026-09-12.** Originally, if the SOURCE side (local for Push, Dropbox for Pull) was unchanged since the manifest's last-confirmed state, the code did nothing at all for that file — even if the destination side had lost it (deleted there by hand outside this tool, or an earlier push/pull silently failed after the manifest already recorded success). Found while diagnosing a real report of manually-created subfolders not appearing on Dropbox after Push (that specific case turned out to reproduce fine — this is a narrower, separately-real gap caught along the way). Now: source-unchanged + destination-missing re-copies the file instead of silently no-op'ing forever. Deliberately **not** a conflict — the source side never changed, so there's nothing ambiguous to protect against, and copying to a side that's merely missing the file can never destroy a newer edit the way a mirrored delete could. Doesn't affect a normal first-ever sync (no `recorded.dropbox`/`recorded.local` entry yet) — see the two "never confirmed" regression tests in `file-sync.test.js` guarding against double-counting that case.
- **Push/Pull refuse a job's own subfolder.** Pointing the Job Folder field at `0 RAW`, `HDR Photos`, etc. instead of the job's top-level folder used to silently create a disconnected top-level Dropbox folder literally named `"0 RAW"`/`"HDR Photos"` (found in real use, 2026-09-08 — this actually happened in the studio's live Dropbox). `looksLikeAComponentFolderNotAJobFolder()` checks the selected folder's name against `folder-builder.js`'s known component-folder names and refuses with an explanation instead. Deliberately **not** implemented as "require `job.json` to exist" — that would break the legitimate case of Pulling into a freshly-created empty folder to bootstrap a job onto a new machine.
- **Job ID collision across machines, mitigated 2026-09-15 (`getNextJobIdChecked`, not a full fix).** `id-generator.js`'s `getNextJobId()` only scans the CONFIGURED Job Root Folder on the machine it's running on. Job Generator now runs on more than one machine at once — a local test copy on this Mac, and Franky's own separate install on his Windows PC — with no shared filesystem between them, so each machine's "what's the next free ID today" check is blind to the other. Real incident: a local test job (in `job-generator/test-output/`, this Mac's default Job Root Folder when `.config.json` is absent) and a real client job Franky created on his machine both independently computed `FVS-20260915-001` the same day and collided on Dropbox — their photo-sync-worker Supabase records merged into one `projects` row. **Mitigation**: `getNextJobId` itself is unchanged (still local-only, still synchronous, still the thing the tests exercise directly); a new `getNextJobIdChecked(root, date, checkFn)` wraps it and, given a working `checkFn`, bumps the sequence until `dropbox-sync.js#jobIdExistsOnDropbox` (checks the SAME Dropbox account both machines share, via the jobId property-tag search) reports no collision. Wired in at `server.js`'s `/api/create-job` only — NOT `/api/plan`'s live preview, to keep every keystroke's preview instant rather than adding a Dropbox round-trip to it; the preview ID can therefore occasionally differ by one from what actually gets assigned. Best-effort only: if Dropbox is unreachable/unconfigured, `checkFn` reports `checked:false` and the local candidate is used as-is, same as before this fix. **The real fix is moving ID assignment to a shared backend** once job-generator is online (see `franvision-architecture-strategy-decision.md`) — this is a stopgap, not the end state, and the two now-orphaned collision artifacts (a stray property tag manually removed from the test folder, a bogus test `address` value manually reverted on the real job's Supabase row) were cleaned up by hand this session, not by any new code.
- **Push/Pull against a wrong (e.g. mis-decoded Chinese) `jobFolderPath` used to report a false "0 uploaded, 0 deleted" success instead of an error, fixed 2026-09-15.** `file-sync.js#walkFiles()`'s inner recursive `walk()` catches a `readdirSync` failure and skips that subtree rather than throwing — correct for a permission-denied NESTED subfolder mid-walk, but the exact same catch also covered the TOP-level call (`jobFolderPath` itself unreadable/nonexistent), silently treating "wrong path entirely" the same as "empty folder." Found in real use on the Windows package: a Chinese client name round-tripped through the win32 folder-picker (see `pickFolderNative()`, fixed the same day on the `windows-package` branch) came back mis-encoded, so Sync's "Job Folder" field held a path that didn't exist on disk — `walkFiles()` silently reported zero local files, and since the (equally wrong) Dropbox-side lookup also found nothing, Push/Pull concluded "0 uploaded, 0 deleted" as if the sync had genuinely succeeded. Fixed: `walk()` now re-throws when the unreadable directory is the top-level call (`relParts` still empty) — caught by `pushJobFilesToDropbox`/`pullJobFilesFromDropbox`'s own try/catch and turned into a proper `{success:false, error}` (e.g. surfacing `ENOENT: ...`) instead of a false success. A genuinely permission-denied NESTED subfolder mid-walk is unaffected — still skipped, not thrown.
- **`MLS` renamed to `HDR Photos` (2026-09-12).** Pure naming change to the always-present component folder that holds the studio's finished high-res photos — no behavior change, no folder moved or removed, `getComponentFolders()` still returns it unconditionally in the same position. Motivation: "MLS" as a folder name was confusing right next to the Delivery Email's own, unrelated "MLS Photos" line (which points at Photo Sync Worker's derived `MLS for download` folder — a different thing entirely). This is a **go-forward rename, not a migration** — jobs created before 2026-09-12 keep a real `MLS` folder on disk/Dropbox, so both names are kept everywhere a component-folder name is matched against: `file-sync.js`'s `KNOWN_COMPONENT_FOLDER_NAMES` lists both (same treatment as the `Home Report` naming-mistake residue above), and `photo-sync-worker/wrangler.jsonc`'s `SYNC_FOLDERS`/`DOWNLOAD_SET_FOLDERS` were updated to watch both `MLS` and `HDR Photos` and redeployed 2026-09-13 (see photo-sync-worker/CLAUDE.md) so neither old nor new jobs stop syncing. **Known gap, accepted, not built around**: `delivery-email.js`'s HDR line always points at `HDR Photos` — running Job Update on a pre-2026-09-12 job (which still has `MLS`, not `HDR Photos`) creates a new, empty `HDR Photos` folder and links the Delivery Email's HDR line to that, not to the old `MLS` folder where the real photos actually are.
- **Deferred, not yet built**: a `jobStatus` field + auto-triggering a final sync when a job's status changes. The user wants this but said the field design itself is still TBD — do not invent either the field or an auto-trigger mechanism until that design is given.
- **Delivery-page folders/files created automatically (2026-09-18).** Three additions, all feeding delivery-page/photo-sync-worker's "drop a file in Dropbox, no data entry" pattern (see `delivery-page/CLAUDE.md`'s "Manual photo overrides are Dropbox folders"):
  - **`Cover&Closing` — Dropbox-only, top-level.** Where staff put the 1-2 photos hand-picked from the All-in-One gallery as the delivery page's cover/closing shots (lowest filename = cover, highest = closing). Same shape as `MLS for download`: pre-created empty on Dropbox only (`dropbox-sync.js#ensureCoverClosingFolder`, via the shared `ensureDropboxOnlyFolder`), never on local disk, in `file-sync.js`'s `DROPBOX_ONLY_FOLDER_NAMES` so Push/Pull skip it. Created in the same real-Job-ID-only block as `MLS for download` (not for Drafts); an Update re-runs it, so older jobs pick it up the next time they're updated.
  - **`HDR Photos/Callout` — a normal component folder** (`folder-builder.js`, nested under `HDR Photos`, local + Dropbox + Push/Pull like any other) for the delivery page's Callout section photos. Present 2026-09-18..2026-09-22 on EVERY job unconditionally; **narrowed 2026-09-22 to only Walkthrough Video, Vlog Video, or Drone Photos** (`getComponentFolders()`'s `wantsCallout`) so a plain photo-only job stops getting an empty folder nobody fills. `Callout` was added to `file-sync.js`'s `KNOWN_COMPONENT_FOLDER_NAMES` (mis-pick guard) — unaffected by the narrowing since it's still a real possible folder name. For pre-rename jobs that still have `MLS`, Callout (when it applies) lands under a newly-created `HDR Photos` (same accepted gap as the HDR line, see the MLS-rename bullet).
  - **`Tour Link.txt` — Dropbox-only, tied to the 3D Virtual Tour checkbox.** An **empty** file at the job root on Dropbox (`dropbox-sync.js#ensureTourLinkFile`: `filesUpload` with `mode:add`, no autorename — an existing file, e.g. a link already pasted in, comes back as a conflict = success and is never overwritten). photo-sync-worker's `tour-link-sync.js` writes its trimmed text into the page's `tourUrl`, so it's empty on purpose (a placeholder sentence would be published as the URL). Staff paste the link straight into it on Dropbox; it is **never created locally and never synced** (`file-sync.js`'s `DROPBOX_ONLY_FILENAMES`, so Push skips it and Pull won't download it). Created in the real-Job-ID-only block when `three_d_tour` is selected; **deleted (`removeTourLinkFile`, taking any pasted link with it — explicit request) only on the Update where 3D goes from checked → unchecked** (compared against the previous `job.json` services), so a `Tour Link.txt` on a job that never had 3D (e.g. a Floor Tour link pasted by hand) is left alone. Response field `tourLink`. Floor Tour is not covered (only `three_d_tour`). (First version created it locally instead; changed same day — a local-only copy needed a Pull/Push round trip to reach the worker for no benefit.)
- **Job Generator "online", stage 1 (2026-09-19, branch `jg-online-supabase`): the SERVER assigns Job IDs and stores job/draft metadata.** Motivated by the 2026-09-15 cross-machine ID collisions (Mac + Franky's Windows scanned only their own folders). Explicit decisions: **no offline job creation and no temporary IDs** — Dropbox needs the network anyway, so Create Job / Save Draft / Update are *refused* (503, before anything is created) when the server can't be reached; **no roles/permissions yet** (only Franky + Siyuan use the tool) but access is already token-gated so real login can replace it later; **old jobs are NOT imported** (the ID allocator takes a `floor` = highest sequence found in local folders, and the existing Dropbox `jobIdExistsOnDropbox` check stays as a best-effort extra, so legacy IDs are never reissued); drafts DO live on the server so a draft saved on the Mac opens on the Windows desktop.
  - **Schema `supabase/schema.sql`** (run once in the SAME Supabase project as FSB/photo-sync-worker; NOT applied automatically): `jg_jobs` (one row per job or draft, natural key `folder_name`, `job_id` NULL for a draft and **write-once** — a real ID is never replaced or cleared, `data = {job: <job.json>, form: <form-state>}`), `jg_job_counters` (per-day sequence), `jg_tokens` (sha256 of one secret per machine). RLS ON with **no policies**, so the public anon key reads/writes nothing directly; the only way in is `SECURITY DEFINER` RPCs (`jg_allocate_job_id`, `jg_peek_job_id`, `jg_upsert_job`, `jg_get_job`, `jg_list_jobs`, `jg_delete_draft`) that each require the caller's token. Deleting a machine's `jg_tokens` row revokes it. (Chosen over a Cloudflare Worker middle layer: two trusted users don't justify another deployable, and this keeps the full DB key off every machine.)
  - **`job-backend.js`** (RPC client; `JG_SUPABASE_URL`/`JG_SUPABASE_ANON_KEY`/`JG_TOKEN` in `.env`, all three or it's disabled and everything behaves as before) and **`job-sync.js`** (row⇄app-shape conversion, `resolveExisting` = server row first / local folder fallback with a hard **conflict** when the two hold different real IDs, `allocateJobId`). `test-support/fake-job-server.js` is a dev-only stand-in for the RPCs (two "machines" = two `rootFolder` values) — not part of the unit tests.

- **`refreshFolderPreview()`'s out-of-order-response bug (found and fixed 2026-09-09), same class as the earlier commission bug below.** Fast typing in Client Name/Address/Shoot Date fires one `/api/plan` request per keystroke; responses aren't guaranteed to resolve in order, so a stale one could land after a newer one and show a mid-keystroke folder name. Fixed with the same `*RequestSeq` monotonic-counter guard `refreshCommission()` already used.
- **The Shoot Notes textarea + image upload (added 2026-09-08, reworked into `calendar-file.js` the same day) exist for exactly one purpose: generating a `.ics` calendar file for the shoot.** The images are NOT reference/inspiration photos — typically a lockbox/gate code or a screenshot of instructions the listing agent sent. Neither notes nor images are mirrored into `job.json` or `Job Info.txt` in any form, and neither is synced to Dropbox — `Shoot Schedule.ics` is in `file-sync.js`'s `LOCAL_ONLY_FILENAMES` alongside `job.json`/`Job Info.txt` (the pre-2026-09-10 `Shoot Info` FOLDER, which held the .ics + loose image files, is still in `LOCAL_ONLY_FOLDER_NAMES` for any lingering old jobs). An even earlier version wrote notes/images into a synced `Shoot Notes` folder and into `job.json`/`Job Info.txt` — that was wrong; don't reintroduce it.
  - **Shoot Time is optional** — the existing Shoot Date field is date-only, so a separate `shootTime` field (`HH:MM`, 24-hour, `validate.js#isValidShootTime`) was added for this. Leaving it blank means "don't generate a calendar file" — `calendar-file.js#writeCalendarFile()` returns `null` and nothing is written, so any notes/images collected in that case are simply not persisted anywhere (their only destination is the calendar event).
  - **The Shoot Time input is a plain text field (`placeholder="HH:MM"`), not `<input type="time">`** — deliberately, matching Shoot Date's own treatment. A native time input's displayed format (12h w/ AM/PM vs 24h) depends on browser/OS locale, and a native 12h picker left with the AM/PM segment unset silently reports its `.value` as `''` (indistinguishable from "intentionally blank") — found in real use (2026-09-09): a real Shoot Time was typed but AM/PM was never selected, so no calendar file was generated with zero error shown. Fixed by switching to plain text + `validate.js#isValidShootTime` (same regex client- and server-side) + a visible inline error (`#shootTime-error` in `public/index.html`) the moment something non-blank and malformed is typed, instead of silently doing nothing. The field also auto-inserts the colon as you type (see the input-helpers bullet above).
  - **`writeCalendarFile()` also validates Shoot Date is present and well-formed the moment Shoot Time is given** (added 2026-09-09, alongside the fix above) — before this, a Shoot Time with a blank/malformed Shoot Date (possible via a Draft, which allowed a blank Shoot Date at the time) silently produced a corrupt `.ics` (`DTSTART:undefinedundefinedT140000`, `DTEND:NaNNaNNaNTNaNNaNNaN`) instead of failing loudly. Now throws a clear error instead. (Since the 2026-09-13 Draft/Job unification above, a Draft goes through `/api/create-job` and so always requires a valid Shoot Date regardless of Shoot Time — this historical gap can no longer occur.)
  - **Images are LINKS in the `.ics` DESCRIPTION (since 2026-09-21), not attachments.** The old base64 `ATTACH` only showed in Apple Calendar / classic Outlook; Google Calendar and new Outlook ignored it. `calendar-file.js#buildDescription` = notes, blank line, then `图片 Images:` + numbered filename/URL lines (bare URLs so every calendar auto-links them). `writeCalendarFile` REFUSES an image without a `url` (it must be uploaded first — see the stage-2 bullet). `readImagesFromIcsFile` still parses legacy ATTACH.
  - The event defaults to a 2-hour duration (`DEFAULT_DURATION_MINUTES`). **DTSTART/DTEND/DTSTAMP are real UTC (`Z`-suffixed)**, computed from the HOST machine's own configured timezone via `new Date(y, mo, d, hh, mm)` (correct for that exact date, DST included — no manual timezone table needed) — `calendar-file.js#parseLocalShootDateTime()` / `formatUtcStamp()`. **This was a floating local date-time (no `Z`, no `TZID`) until 2026-09-10** on the theory that "the user imports it by hand on their own machine, so there's no timezone to reconcile" — found wrong in real use on Windows: the calendar app used to open the file did not treat the floating time as "local, whatever that means to you," and displayed a time that didn't match what was typed. Floating-time handling is inconsistent across real calendar clients; UTC has no such ambiguity anywhere. Do not revert to floating time.
  - Images still arrive from the browser as base64 in the same JSON body as the rest of `/api/create-job` (no multipart parsing in this zero-dependency server) — see `server.js`'s `MAX_REQUEST_BODY_BYTES` cap, sized off `calendar-file.js`'s own limits.
  - **Calendar event title (SUMMARY) naming rule, added 2026-09-16 (user's own business convention), replacing the old `"Photo Shoot -- <client>"`.** Format: `<package code>_<client name>_<photographer code>`, e.g. `HDR P+V+D_Paul_jo` (Luxury Photos + Walkthrough Video + Drone, client Paul, shot by Johnson). `calendar-file.js#buildEventTitle()` / `buildPackageCode()` / `photographerCode()`:
    - **Package code** is `order.photography` (`P` for `'standard'`, `HDR P` for `'luxury'`) plus a fixed-order `+`-joined list of addon codes, each included only if ordered: Walkthrough Video (`V`) or Vlog Video (`Vlog`, never both — same either/or assumption `delivery-email.js#getDeliverableLines()` already makes), Drone (`D`, `addons.drone_photos`), 3D Tour (`3D`, `addons.three_d_tour`), Floor Plan or Site Plan (`fl`, shared code — `site_plan` requires `floor_plan` anyway), Feature Sheets (`FS`). This order (photography, video, drone, 3D, floorplan, feature sheets) was confirmed with the user, not just inferred from their one example. `virtual_staging` has no code in this naming rule and contributes nothing to the title.
    - **Photographer code**: `franky`→`F`, `johnson`→`jo`, `jason`→`j`, `elsa`→`E` (matched case-insensitively against the free-typed, optional Photographer Name field). Anyone else gets their name's first two letters, capitalized like a name (`"Mike"`→`"Mi"`) — confirmed with the user specifically so a new/guest photographer's job still gets a distinct title instead of a generic or silently-dropped one. A blank Photographer Name (the field is optional) becomes the literal placeholder `？` (full-width, matching the user's own wording) rather than omitting the segment — keeps the title's three-part shape consistent rather than ending in a bare trailing `_`.
- **`server.js#readJsonBody()` mojibake bug with Chinese (or any multi-byte-UTF-8) Client Name/Address, found and fixed 2026-09-14.** It used to build up the request body with `data += chunk` — string-concatenating each raw `Buffer` chunk directly implicitly calls that chunk's OWN `.toString('utf8')` in isolation, and a multi-byte character split across a TCP chunk boundary decodes as U+FFFD replacement bytes on both sides of the cut instead of the original character. This landed intermittently, not on every job — whether a given multi-byte name got corrupted depended on where the chunk boundary happened to fall, which is more likely to happen on a larger request (e.g. one carrying Shoot Notes images). Fixed by collecting raw chunks into an array and decoding once via `Buffer.concat(chunks, bytes).toString('utf8')` after `req`'s `'end'` event, so no multi-byte character is ever decoded from an incomplete byte sequence. **A job folder already created with a corrupted (mojibake) name is not retroactively fixed by this** — use the "unlock identity fields" rename-in-place escape hatch (see the Draft/Job unification bullet above) to rename it once corrected.
- **`fs.renameSync` in the identity-unlock rename path now retries transient Windows lock errors, added 2026-09-14.** Renaming a folder right after touching it can throw `EPERM` on Windows if Explorer has it open, a cloud-sync desktop app (Dropbox/OneDrive) is scanning it, or antivirus is indexing it — found in real use trying to rename a folder to fix the mojibake bug above. `server.js#renameFolderWithRetry()` retries `EPERM`/`EBUSY` a few times with a short delay before giving up; a rename that still fails after retries surfaces a clear 409 message ("close anything using it and try again") instead of the raw Node error text the outer try/catch used to leak verbatim.

## Wave invoicing (2026-09-23, optional -- see `wave-backend.js`)

Three pieces, all optional and independent of each other working: unconfigured, the picker is hidden and no invoice is ever created, and nothing else in Job Generator changes.

- **Customer picker.** `GET /api/wave-customers?q=...` (`wave-backend.js#searchCustomers`) -- Wave's API has no server-side name search (only exact `email`), so the whole customer list (~300 rows) is fetched once and cached in-memory for 5 minutes, filtered here. The "Bill To (Wave Customer, optional)" field in the Client Information panel (`public/index.html`) is hidden entirely unless the server reports `configured:true`; picking one stores `{id, name}` in the page-level `selectedWaveCustomer`, sent as `waveCustomerId`/`waveCustomerName` on Create/Update Job.
- **Duplicate customers are hidden from the picker (2026-09-23).** Wave can't delete a customer that has invoices (`customerDelete` -> "invoice conflict", tested), so the Wave customer cleanup marked duplicates by renaming them `[重复] <name>`; `listAllCustomers` skips any name starting with that prefix (`DUPLICATE_PREFIX`), so only the canonical customer (correct case, most complete info) is pickable. Invoice-less duplicates were deleted outright. `scripts/wave-customer-dedupe.js` (read-only) lists suspected duplicate groups for a human to confirm before any rename.
- **Custom Items.** Free-form one-off invoice lines (e.g. Road Fee) -- name + amount, add/remove rows under the Manual Adjustment fieldset. Their sum is folded into `order.manualAdjustmentCents` client-side (`readOrder()`) BEFORE `/api/plan`/`/api/create-job` ever see it, so the engine's total already includes them with no changes to `pricing/engine.js`. Reopening a job (`applyOrderToForm(order, customItems)`) does the inverse -- subtracts the loaded `customItems`' sum back out of `manualAdjustmentCents` before filling the Manual Adjustment field, then rebuilds the rows -- so nothing double-counts. **2026-09-23 decision: no per-name Wave product is created for a custom item** (a `wave-client.js#ensureProduct` find-or-create-by-name approach was built, then explicitly reverted) -- every custom item uses the generic `custom_item` ("Other")/`adjustment_discount` ("Discount") product, its name always in the line's description.
- **Auto-create-and-approve / patch an invoice on Create/Update Job**, gated by `WAVE_AUTO_INVOICE` (default OFF) AND a picked Wave customer. No `wave.invoiceId` saved on the job yet -> `invoiceCreate` as DRAFT, then `invoiceApprove` **immediately** (2026-09-23: no manual Approve step in Wave any more; if the approve call fails the DRAFT is kept and `pendingConfirmation` says to approve it by hand). An invoice id already saved -> `invoicePatch` in place, **approved or not** -- Wave allows editing approved (`SAVED`) invoices (verified 2026-09-23 against a Personal-business test invoice; status stays `SAVED`). `wave-backend.js#buildAndSubmitInvoice` checks the invoice's LIVE status via `getInvoice` (not the possibly stale one in job.json) and refuses only `PAID`/`PARTIAL` (payment already applied) -- flagged in `pendingConfirmation`, existing invoice left untouched; a still-`DRAFT` invoice is approved after the patch. Result persists in job.json's `wave` field (`{invoiceId, viewUrl, invoiceNumber, status, updatedAt}`), carried forward on later edits the same way `completedAt` already is (see `previousWave` in `server.js`) -- a failed attempt never loses a previously-created invoice's id.
- **Positive un-itemized price adjustment is folded into the FIRST invoice line's price** (`wave-invoicing/invoice-request.js`, 2026-09-23) instead of getting its own "Price adjustment" line; a negative one still gets a visible Discount line, and named Custom Items (e.g. Road Fee) still each get their own line.
- **New customer from the picker** (2026-09-23): "+ New" button / the "+ New customer" item shown when a search finds nothing opens an inline form (name required; email/phone/address optional -> `wave-backend.js#createCustomer` -> Wave `customerCreate`, address goes in `addressLine1`), and the created customer is selected straight away (and added to the cached list).
- **Suggested customer from pairing history + fuzzy Wave-name match** (2026-09-23; fuzzy part 2026-09-24): after the history matches, `/api/wave-suggest` also fuzzy-matches the Client Name against Wave's own customer list (`wave-match.js`: same name, one contains the other, same words reordered, small typos; some inaccurate suggestions accepted by the user) -- so a client with no history still gets suggestions. Chips show just the Wave customer name (a "similar name" note only on history matches whose stored client name differs).
- **Suggested customer from pairing history** (2026-09-23): typing a Client Name shows "Suggested: <Wave customer>" chips (`GET /api/wave-suggest`, never auto-selected -- one click to accept). History = shared Supabase table `jg_wave_pairings` (RPCs `jg_record_wave_pairing` / `jg_suggest_wave_pairings` in `supabase/schema.sql`, job-backend.js wrappers): every Create/Update of a REAL job (not a Draft) with a picked customer +1s the (normalized client name, Wave customer) pairing; exact-name matches rank first, then "one name contains the other" (3+ chars); the SQL also back-fills once from existing `jg_jobs` rows that carry a `waveCustomerId`. Reopening a job now restores its Wave customer into the picker (before, an Update after reopening sent no customer and skipped the invoice). **The new SQL must be applied to the production Supabase project by hand (SQL editor) before suggestions work** -- without it `/api/wave-suggest` just returns an empty list and recording is silently skipped.
- **`wave-product-map.json`** (gitignored, see `.example`) maps `pricing-config.js` service/package ids + `adjustment_discount`/`custom_item` to real Wave product ids in the target business -- built once via `wave-probe/setup-real-products.js --apply` (core-schema branch; not yet merged to main). Without this file, the picker/search still work (`isConfigured()`) but no invoice can be built (`canBuildInvoices()` is false) -- `buildAndSubmitInvoice()` throws a clear `ENOENT`, caught and reported in `pendingConfirmation`, never blocking Create/Update Job itself.
- **Not yet built:** reconciling e-Transfer payments; a Wave-based agent/billing-party directory (see the separate `core-schema` design work) -- the picker searches Wave's own customer list directly, nothing is mirrored into Supabase yet.

## Environment / secrets

Dropbox features (`dropbox-sync.js`, `file-sync.js`, `delivery-email.js`) need `job-generator/.env` (gitignored; copy from `.env.example`): `DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, `DROPBOX_REFRESH_TOKEN` (long-lived; the SDK mints short-lived access tokens itself — never hardcode a short-lived token), `DROPBOX_TEMPLATE_ID` (printed once by `scripts/setup-dropbox-template.js` — re-running that script is safe, it detects and reuses an existing "FranVision Job" template rather than duplicating it). All Dropbox calls go through `dropbox-sync.js#getClient()`/`isConfigured()` — don't construct a second `Dropbox` client elsewhere. `dotenv.config()` is always called with `quiet:true` (dotenv 17.x otherwise prints a self-promotional console line on every load).

**`delivery-email.js`'s shared-link generation (`sharingCreateSharedLinkWithSettings`/`sharingListSharedLinks`) needs the app's OAuth token to carry the `sharing.write` scope** — unlike `dropbox-sync.js`'s/`file-sync.js`'s calls, which are all covered by `files.metadata.read/write` + `files.content.read/write`. If the "FranVision OS" app's current refresh token predates this feature, add `sharing.write` in the Dropbox App Console (App permissions tab) and re-run the OAuth flow to mint a new refresh token — until then, every link falls back to its placeholder token (best-effort, does not block job creation, but every link will be missing).

`scripts/check-job-properties.js <dropbox-path>` is a standalone debug utility — reads back a folder's hidden `jobId` property via the real API, useful for manually confirming a specific job's Dropbox state.

## Known limitations

- Push/Pull run synchronously within one HTTP request and return one final summary — no progress streaming for a large first-time sync of many/large files.
- The chunked-upload-session path (files >140MB) is unit-tested only against a fake client (exact byte-offset/sequence assertions) — never verified against a real 140MB+ file (deliberate, to avoid burning real time/bandwidth on an expensive test).
- **Editing an identity field (Shoot Date / Address / Client Name) of an already-created job makes a NEW job, not an edit — by default.** Job identity IS `buildJobFolderName()`'s output (those 3 fields), so changing one changes the canonical name → no match → new folder + new Job ID; the old folder is orphaned and must be deleted by hand. Accepted limitation (see "Job Update" below and `DESIGN-job-update.md`). Everything else about a job IS editable in place — re-enter the same 3 fields and click Create Job (it becomes "Update FVS-…"). **As of 2026-09-13, the UI actively prevents hitting this by accident**: these 3 fields are locked (read-only) once the form represents a real job, and the only way around the lock — an explicit "unlock" checkbox — renames the existing folder in place (local + Dropbox) instead, keeping the same Job ID (see the Draft/Job unification bullet above). The underlying "identity edit = new job" behavior described here is unchanged; what changed is that it now takes a deliberate opt-in to trigger it at all.
- **No Windows support on `main`** (macOS only) — a launcher (`Job Generator.bat`) + PowerShell folder-picker branch in `pickFolderNative()` were built and tested on macOS but are being kept off `main` deliberately for now (see "Running it" above); `run-tests.js` (the cross-platform test runner `npm test` uses) is NOT part of that exclusion — it's merged and works identically on macOS.
- **Wave payment link in the Delivery Email is auto-filled as of 2026-09-23, but ONLY when `WAVE_AUTO_INVOICE` is on AND a Wave customer was picked** (see "Wave invoicing" above) — otherwise it's still the old manual fill-in placeholder, same as before that existed. Since the invoice is now approved automatically, the link is live as soon as it's filled in; if the approve step failed (`pendingConfirmation` says so) approve the invoice in Wave before sending the email.
- **The Home Report line in the Delivery Email never appears right now** (not "effectively always included" — that was true before the Home Report folder-generation fix; see the "Delivery Email" decision above) — correct behavior until the real Home Report service exists in `pricing-config.js`.
- **Running Job Update on a job created before the 2026-09-12 `MLS`→`HDR Photos` rename links the Delivery Email's HDR line to the wrong folder** — a new, empty `HDR Photos` gets created (per the normal Update folder-diff logic) and linked, while the job's real photos stay in the old `MLS` folder. See the `MLS` renamed to `HDR Photos` bullet above. Not built around; fix by hand (move the photos, or just keep using the old `MLS` folder for that job).

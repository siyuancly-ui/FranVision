# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this directory (`job-generator/`). See the repo-root `CLAUDE.md` for how this module fits into the rest of FranVision.

## What this is

A local, double-click-to-run tool for a real estate photography studio. Given a client/property/shoot-date/service selection, it:
1. Computes pricing via `pricing/engine.js` + `pricing/pricing-config.js` (never reimplemented here — see `pricing-adapter.js`)
2. Computes a photographer commission via an independent rate engine (never touches pricing)
3. Generates a unique Job ID (`FVS-YYYYMMDD-XXX`, increments per day)
4. Creates a standardized local folder structure
5. Writes `Job Info.txt` (human-readable) and `job.json` (machine-readable, integer cents)
6. Optionally generates a `.ics` calendar file for the shoot from an optional Shoot Time + free-text notes + images (e.g. a lockbox code or a screenshot of the agent's instructions)
7. Optionally mirrors the folder skeleton + files to Dropbox, and can later push/pull local ↔ Dropbox two-way for an existing job
8. Generates two **Delivery Email** `.txt` files (Chinese + English) with Dropbox shared links for whichever deliverables were ordered auto-filled in — an interim, transitional stand-in for the eventual client delivery page (see root `CLAUDE.md`'s long-term vision). See `delivery-email.js`.

Before any of the above is finalized, the whole form can also be saved as a **Job Draft** (`draft-store.js`) — for a shoot whose date/time, package, or assigned photographer isn't locked in yet. A draft never creates a job folder/job.json/Dropbox mirror; it only writes its own small local record (plus, once Shoot Time is set, a draft calendar file) under `job-generator/drafts/`, and gets deleted once you click Create Job to finalize it into a real job.

job-generator is expected to eventually be ported into the Wix/Velo backend (see root `CLAUDE.md`) — nothing here is that port yet, but keep that in mind when choosing a data shape for anything new (e.g. `draft-store.js`'s record is a clean, filesystem-agnostic JSON object for exactly this reason).

## Running it

```bash
cd job-generator
npm install          # only needed once, or after pulling changes to package.json
node server.js        # -> http://localhost:4173
```

Or double-click `Job Generator.command` (macOS) at the repo root. There is no Windows launcher currently -- an earlier attempt (`windows-support` branch, never verified on real Windows, never pushed) was deliberately abandoned and deleted 2026-09-08 as too stale against current code; Windows support would need to be rebuilt fresh if wanted again.

## Tests

No test framework — each `*.test.js` file is a self-contained script using plain Node `assert` + a hand-rolled pass/fail runner (`node <name>.test.js`). Run the whole suite:

```bash
cd job-generator
for f in *.test.js; do node "$f" || echo "FAILED: $f"; done
```

As of 2026-09-11 this is 262 tests across 13 files, all passing. Dropbox-touching modules (`dropbox-sync.js`, `file-sync.js`) never hit the real API in tests — every async orchestrator function accepts an injectable `client` (and `downloadImpl`/`thresholds` where relevant) so tests supply a fake Dropbox client object instead. **When verifying Dropbox behavior beyond what the fake-client tests cover, you are testing against the studio's real, live production Dropbox account** (confirmed directly — hundreds of real client job folders live at the account root) — always use an obviously-fake job name, and always clean up (`filesDeleteV2`) whatever you create before finishing.

## Architecture: module map

Every module below is plain Node (`module.exports`), most also loadable as a browser `<script>` (UMD pattern, `window.X`) for the ones the client-side UI needs directly — those are whitelisted in `server.js`'s `SHARED_FILES` map and served at `/shared/*.js`.

| File | Role |
|---|---|
| `sanitize.js` | Cross-platform-safe folder/file names; `buildJobFolderName()` — the one place the top-level job folder name is constructed |
| `validate.js` | `isValidShootDate()` — strict `yyyy/mm/dd`, real calendar validation |
| `id-generator.js` | `FVS-YYYYMMDD-XXX` (`getNextJobId`), source of truth is scanning each job folder's `job.json` (not folder names) for today's max sequence; also `findExistingJob(root, folderName)` — the "is this an UPDATE of a job that already exists?" check |
| `folder-builder.js` | `getComponentFolders(order)` (pure) + `createJobFolders()` (fs) — the **single source of truth** for "what folders a job needs"; both local creation and the Dropbox mirror consume its output. Also `diffComponentFolders(newOrder, oldOrder)` + `folderHasRealFiles()` for the update path |
| `pricing-adapter.js` | Thin wrapper around `pricing/engine.js` + `pricing/pricing-config.js` — never reimplements pricing |
| `commission-config.js` / `commission-engine.js` | Photographer commission — **entirely independent from pricing**, no shared code or state |
| `job-files.js` | Writes `Job Info.txt` + `job.json`; owns `computePendingConfirmation()` |
| `calendar-file.js` | Optional `.ics` calendar file for the shoot (Shoot Time + free-text notes + images), written as `<job folder>/Shoot Schedule.ics` with images embedded as base64 `ATTACH` — NOT part of the `order` shape (free-form job context, not a service selection) |
| `draft-store.js` | Job Drafts — save/load/delete the whole form before a shoot is finalized; reuses `calendar-file.js` unchanged, pointed at the draft's own folder |
| `config-store.js` | Persists the default Job Root Folder to `.config.json` |
| `dropbox-sync.js` | Best-effort: `syncJobFolderToDropbox` creates the empty Dropbox folder skeleton + tags it with a hidden `jobId` property; `updateJobFoldersOnDropbox` adds newly-needed folders and prunes no-longer-needed EMPTY ones on an update; `ensureMlsForDownloadFolder` + `createSharedLink` back `delivery-email.js` (see below) |
| `file-sync.js` | Two-way Push/Pull of actual file *contents* for an **existing** job, any time after creation, as many times as needed |
| `delivery-email.js` + `delivery-email-template.zh.txt` / `.en.txt` | Generates the two Delivery Email `.txt` files at Create/Update Job time — see the "Delivery Email" decision below |
| `server.js` | Node `http`, zero framework, wires all of the above into a small JSON API |
| `public/index.html` | The UI — plain JS, no framework, no build step |

All of `folder-builder.js`, `pricing-adapter.js`, and `commission-engine.js` are driven by the **same `order` shape** (`{propertyType, photography, addons}`) — this is deliberate: one selection model feeds folders, pricing, and commission defaults instead of three parallel ones.

## Confirmed design decisions (do not "fix" without re-reading this — several of these were tried the "obvious" way first and explicitly reverted)

- **Photographer Name is optional at job creation.** Client Name, Address, Shoot Date, Job Root Folder, and a valid service selection block the Create button; Photographer Name does not.
- **Virtual Staging folder creation is decoupled from its pricing qty.** Checking the box creates the folder immediately even at qty 0 (photo count often isn't known until after the shoot) — `folder-builder.js`'s rule is `!!addons.virtual_staging || stagingQty > 0`, not `stagingQty > 0` alone.
- **`pendingConfirmation`** (`job-files.js#computePendingConfirmation`) is the single mechanism for "allowed to be incomplete now, must be caught before invoicing" — currently covers: missing Photographer Name, unconfirmed Virtual Staging qty, and a failed/skipped Dropbox sync. Surfaced in `job.json`, `Job Info.txt`, and the UI's success panel. There is intentionally **no** separate "mark job complete" workflow yet.
- **Twilight and 3D Tour have no dedicated folder** (removed 2026-09-06) — Luxury tier still gets `0 RAW/4 Raw HDR`, `three_d_tour` is still a real priced pricing-config.js addon, neither gets a folder anymore.
- **`Local Report`** is an always-present, empty, top-level folder (added 2026-09-07), same treatment as `Revisions`/`Home Report`.
- **Folder-name date has no leading zero** (`sanitize.js#formatDateForFolderName`, added 2026-09-08): `"2026.9.8 Address_Client"`, not `"2026.09.08 ..."` — matches the studio's existing real-folder naming habit. The Shoot Date **input field** still requires strict zero-padded `yyyy/mm/dd` (unrelated — that's for unambiguous validation, not display).
- **`job.json` and `Job Info.txt` are local-only, never synced to Dropbox** (`file-sync.js`'s `LOCAL_ONLY_FILENAMES`) — explicit requirement, found because they were initially reaching Dropbox incidentally via a later Push.
- **Photographer Commission**: config is keyed **per photographer** (`commission-config.js`), not a single shared rate + one exempt name — a future photographer can get their own rate table, not just an exempt flag. Franky is `{exempt: true}` in config, never a hardcoded name check in the engine. Video (Walkthrough and/or Vlog) always maps to ONE `$50` line item, never doubled. Defaults auto-derive from the order but the user can freely override every checkbox before Create Job.
- **Dropbox sync is always best-effort and must never block local job creation.** `dropbox-sync.js` and `file-sync.js` are designed to never throw — every failure mode comes back as a result object (`{success:false, error, ...}`), never a rejected promise, and callers in `server.js` wrap the calls in try/catch anyway as a second layer.
- **File sync is two explicit directions (Push / Pull), never a single auto-merging action.** A file changed on both sides since the last confirmed sync is a **conflict** — left untouched on both sides and reported, never auto-resolved (not "newer timestamp wins"). Deletions mirror to the other side too, unless the side being deleted *from* also changed since the last sync, which is likewise a conflict rather than a silent delete. This rests on a per-job manifest (`.dropbox-sync-manifest.json`, lives inside the job folder, itself excluded from syncing) recording the **last confirmed state on both sides** per file (`{local: {size, mtimeMs}, dropbox: {rev, size}}`) — the decision logic (`planPush`/`planPull`) is pure and fully unit-tested without any Dropbox client.
- **Push/Pull refuse a job's own subfolder.** Pointing the Job Folder field at `0 RAW`, `MLS`, etc. instead of the job's top-level folder used to silently create a disconnected top-level Dropbox folder literally named `"0 RAW"`/`"MLS"` (found in real use, 2026-09-08 — this actually happened in the studio's live Dropbox). `looksLikeAComponentFolderNotAJobFolder()` checks the selected folder's name against `folder-builder.js`'s known component-folder names and refuses with an explanation instead. Deliberately **not** implemented as "require `job.json` to exist" — that would break the legitimate case of Pulling into a freshly-created empty folder to bootstrap a job onto a new machine.
- **Deferred, not yet built**: a `jobStatus` field + auto-triggering a final sync when a job's status changes. The user wants this but said the field design itself is still TBD — do not invent either the field or an auto-trigger mechanism until that design is given.
- **Job Drafts (`draft-store.js`, added 2026-09-09)**: for a shoot that isn't locked in yet — date confirmed but time TBD, package still being negotiated, a reschedule risk, or who's shooting it undecided. A draft lives entirely under `job-generator/drafts/<draftId>/` (gitignored — real client PII), has no jobId/folders/Dropbox state, and is deleted once finalized into a real job via `/api/create-job`'s `draftId` field — **no draft history is kept** (explicit user decision: the finished `job.json`/`Job Info.txt` already hold whatever was true at the end). Multiple drafts can exist at once (studios track several leads/bookings simultaneously) — the UI's "Job Drafts" panel lists all of them, most-recently-updated first. Saving a draft does NOT validate Shoot Date's format the way `/api/create-job` does (a draft is explicitly for "the date isn't locked in yet"); Shoot Time and images are still validated. A draft's own folder is passed straight into `calendar-file.js#writeCalendarFile()` unchanged (same `Shoot Schedule.ics` a real job gets) — every save regenerates it from scratch from exactly the images/notes/time in that request (no separate add/remove-image endpoint to keep in sync). The client-side image state model (`shootNotesImages` in `public/index.html`) supports two entry kinds — `{kind:'file'}` for a fresh upload, `{kind:'saved'}` for an image read back (as base64) from a loaded draft — normalized to `{filename, dataBase64}` right before either Save Draft or Create Job.
- **Job Update (added 2026-09-10; see `DESIGN-job-update.md` for the full rationale).** Clicking Create Job when a job folder with the same canonical name (Shoot Date + Address + Client Name) already exists is an **UPDATE**, not a second job: it keeps the existing Job ID (`idGenerator.findExistingJob`), preserves `createdAt`, bumps `updatedAt`, recomputes price/commission, and rewrites `job.json`/`Job Info.txt`. `/api/plan` returns `matchesExistingJob` so the UI relabels the button to "Update FVS-…" before the click. Update behavior:
  - **Component folders**: `folder-builder.diffComponentFolders(newOrder, oldOrder)` — newly-needed folders are created; folders no longer in the selection are removed **only if empty** (`folderHasRealFiles` — `.DS_Store`/`~$*`/sync-manifest don't count), otherwise kept and reported in `foldersKeptWithFiles`. Local and Dropbox emptiness are judged **independently** (`dropbox-sync.updateJobFoldersOnDropbox` re-checks on Dropbox) — a folder can be kept locally (has files) but pruned on Dropbox (empty there, not yet Pushed); it self-heals on the next Push. This was an explicit user decision.
  - **Calendar file**: regenerated from the current form state. Added a Shoot Time on the update → `Shoot Schedule.ics` now appears. Cleared the Shoot Time → it's deleted. **Images are preserved across an update** — the update form has no "load existing job" step, so `calendar-file.readExistingImages()` (parses the `.ics` ATTACH lines, + reads a legacy `Shoot Info/` folder) + `mergeImages()` carry forward whatever images the job already had (a fresh upload with the same filename replaces the old one).
  - **Price change** is surfaced in the response (`previousTotalCents`) and shown in the UI ("Total changed: $X → $Y"), never silent.
  - **A folder with the canonical name but no readable `job.json`** → `/api/create-job` returns 409 and refuses, rather than adopting it as a second identity.
  - **Not in scope** (decided 2026-09-10): no "list of created jobs" in the UI (the 3-field auto-match is the only way into update mode), no folder rename on identity-field edit (see the Known-limitation above), no `jobStatus`/"mark complete"/undo.
- **Delivery Email (added 2026-09-11).** Create/Update Job writes two plain `.txt` files into the job folder — `Delivery Email (中文).txt` and `Delivery Email (EN).txt` — merging the studio's existing delivery-email wording (transcribed from "deliverable email template.docx" at the repo root, kept there as the human-readable reference) with this job's client name / address / total price and Dropbox download links. This is an explicitly **interim, transitional** form of the eventual client delivery page (photos + Feature Sheet + video + invoice + payment gate — see root `CLAUDE.md`'s long-term vision); the "which deliverables were ordered → which links go in" logic (`delivery-email.js#getDeliverableLines`) is the same logic that page will eventually need. Design decisions:
  - **Per-deliverable links are real Dropbox shared links, generated automatically** (`dropbox-sync.js#createSharedLink`, "anyone with the link can view", no password/expiry) for the job's corresponding component folder — no manual step. Line → folder mapping: HDR → `MLS`; MLS Photos → `MLS for download` (see next bullet); Video → `Video` or `VLOG` (whichever was ordered — Walkthrough and Vlog are never ordered together on one job, so this never needs to pick between two); Floor Plan/Site Plan → `Floorplan`; Local Report → `Local Report` (always present); Home Report → `Home Report`, gated on it actually being in `componentFolders` (see the Home Report caveat below).
  - **`MLS for download` is pre-created empty on Dropbox at Create/Update Job time** (`dropbox-sync.js#ensureMlsForDownloadFolder`) purely so its shared link can be generated immediately. Normally this folder does not exist until Photo Sync Worker's pipeline writes the first delivery render into it (see `photo-sync-worker/CLAUDE.md`) — waiting for that would mean the link isn't ready at job-creation time. This is **Dropbox-only**: never created on local disk, never listed in `folder-builder.js`'s `getComponentFolders()`, and excluded from Push/Pull's local↔Dropbox mirroring entirely (`file-sync.js`'s `DROPBOX_ONLY_FOLDER_NAMES` — the mirror image of `LOCAL_ONLY_FOLDER_NAMES`) so Pull never downloads a redundant second copy of every MLS photo. Safe alongside Photo Sync Worker's own logic: that folder is already excluded from its `SYNC_FOLDERS` watch list (anti-loop-guard) and its write-back uses `mode:overwrite` at a deterministic path regardless of whether the folder pre-existed.
  - **All-in-One (Zenfolio/CloudPano-style) and Wave payment links stay literal placeholder tokens** (`[请手动填入 All-in-One 链接]` / `[fill in the All-in-One link manually]`, etc.) — no system generates those yet; fill them in by hand. Same fallback for any Dropbox link that fails to generate (Dropbox not configured, network error, missing the `sharing.write` OAuth scope — see Environment/secrets below).
  - **Home Report has no `order`/`pricing-config.js` toggle yet** — `folder-builder.js` currently creates its folder unconditionally (a known bug, to be fixed separately, not by this feature). Until that fix lands, the Home Report line keys off whether `'Home Report'` is present in the job's `componentFolders`, so it is effectively **always included** for now — it will become correctly conditional the moment `folder-builder.js`'s rule is fixed, with no change needed in `delivery-email.js`.
  - **A deliverable that wasn't ordered has its entire line removed** from the output (not left with an empty/placeholder link) — `delivery-email-template.{zh,en}.txt` mark each conditional line with a `{{LINE:KEY}}` prefix that `renderTemplate()` strips or drops the whole line on.
  - **Both files are LOCAL-ONLY** (`file-sync.js`'s `LOCAL_ONLY_FILENAMES`), same treatment as `job.json`/`Job Info.txt`/`Shoot Schedule.ics` — never pushed/pulled/deleted by Push/Pull.
  - **Best-effort, never blocks job creation** — same contract as `dropbox-sync.js`: every function returns `{success:false, error, ...}` rather than throwing, `server.js` wraps the call in try/catch as a second layer anyway, and a failed/partial link generation still writes the `.txt` files (with placeholders for whatever didn't resolve) rather than skipping them.
- **Save as Draft and Create Job are two side-by-side buttons with distinct fills** (`.draft-btn` gold / `.create-btn` dark) in the step-8 panel — deliberately equal visual weight so the draft path isn't reflexively skipped (explicit user request 2026-09-10).
- **Small input helpers (2026-09-10, user request):** Shoot Date has a "Today" button (fills the local date as `yyyy/mm/dd`) and its hint shows today's date. Shoot Time has a light input mask — it strips non-digits and drops the colon in the moment the two hour digits are typed (`14` → `14:` immediately, then `14:30`), so it's visibly clear you don't type `:` yourself; Backspace-aware so the field still clears cleanly.
- **When Create Job would UPDATE an existing job and the current service selection's total differs from that job's saved total, the folder-preview shows "Price will change: saved $X → current selection $Y"** live, before the click — `/api/plan` returns `existingTotalCents` for this. The post-Update result panel also shows the before/after.
- **`refreshFolderPreview()`'s out-of-order-response bug (found and fixed 2026-09-09), same class as the earlier commission bug below.** Fast typing in Client Name/Address/Shoot Date fires one `/api/plan` request per keystroke; responses aren't guaranteed to resolve in order, so a stale one could land after a newer one and show a mid-keystroke folder name. Fixed with the same `*RequestSeq` monotonic-counter guard `refreshCommission()` already used.
- **The Shoot Notes textarea + image upload (added 2026-09-08, reworked into `calendar-file.js` the same day) exist for exactly one purpose: generating a `.ics` calendar file for the shoot.** The images are NOT reference/inspiration photos — typically a lockbox/gate code or a screenshot of instructions the listing agent sent. Neither notes nor images are mirrored into `job.json` or `Job Info.txt` in any form, and neither is synced to Dropbox — `Shoot Schedule.ics` is in `file-sync.js`'s `LOCAL_ONLY_FILENAMES` alongside `job.json`/`Job Info.txt` (the pre-2026-09-10 `Shoot Info` FOLDER, which held the .ics + loose image files, is still in `LOCAL_ONLY_FOLDER_NAMES` for any lingering old jobs). An even earlier version wrote notes/images into a synced `Shoot Notes` folder and into `job.json`/`Job Info.txt` — that was wrong; don't reintroduce it.
  - **Shoot Time is optional** — the existing Shoot Date field is date-only, so a separate `shootTime` field (`HH:MM`, 24-hour, `validate.js#isValidShootTime`) was added for this. Leaving it blank means "don't generate a calendar file" — `calendar-file.js#writeCalendarFile()` returns `null` and nothing is written, so any notes/images collected in that case are simply not persisted anywhere (their only destination is the calendar event).
  - **The Shoot Time input is a plain text field (`placeholder="HH:MM"`), not `<input type="time">`** — deliberately, matching Shoot Date's own treatment. A native time input's displayed format (12h w/ AM/PM vs 24h) depends on browser/OS locale, and a native 12h picker left with the AM/PM segment unset silently reports its `.value` as `''` (indistinguishable from "intentionally blank") — found in real use (2026-09-09): a real Shoot Time was typed but AM/PM was never selected, so no calendar file was generated with zero error shown. Fixed by switching to plain text + `validate.js#isValidShootTime` (same regex client- and server-side) + a visible inline error (`#shootTime-error` in `public/index.html`) the moment something non-blank and malformed is typed, instead of silently doing nothing. The field also auto-inserts the colon as you type (see the input-helpers bullet above).
  - **`writeCalendarFile()` also validates Shoot Date is present and well-formed the moment Shoot Time is given** (added 2026-09-09, alongside the fix above) — before this, a Shoot Time with a blank/malformed Shoot Date (possible via a Draft, which allows blank Shoot Date) silently produced a corrupt `.ics` (`DTSTART:undefinedundefinedT140000`, `DTEND:NaNNaNNaNTNaNNaNNaN`) instead of failing loudly. Now throws a clear error instead; `server.js`'s `/api/drafts` POST pre-checks the same condition for a clean 400 rather than a 500.
  - **Images ARE embedded in the `.ics`** as a standard base64 `ATTACH;FMTTYPE=<mime>;ENCODING=BASE64;VALUE=BINARY;X-APPLE-FILENAME="…";X-FILENAME="…"` property per image (changed 2026-09-10, was: loose files in a `Shoot Info` folder + a DESCRIPTION mention). This is a plain RFC 5545 binary attachment — only the filename hint is client-flavoured. **Apple Calendar and classic desktop Outlook** attach it to the event on import; **Google Calendar and web/"new" Outlook ignore binary ATTACH entirely** (their attachments are a Drive/OneDrive feature, not an .ics one) — there is no .ics-only way to get an image into those. `DESCRIPTION` carries only the notes text. No loose image files on disk any more — the `.ics` is self-contained.
  - The event defaults to a 2-hour duration (`DEFAULT_DURATION_MINUTES`) and uses a floating local date-time (no `TZID`/`Z`) — the user imports this by hand into their own calendar on their own machine, so there's no timezone to reconcile.
  - Images still arrive from the browser as base64 in the same JSON body as the rest of `/api/create-job` (no multipart parsing in this zero-dependency server) — see `server.js`'s `MAX_REQUEST_BODY_BYTES` cap, sized off `calendar-file.js`'s own limits.

## Environment / secrets

Dropbox features (`dropbox-sync.js`, `file-sync.js`, `delivery-email.js`) need `job-generator/.env` (gitignored; copy from `.env.example`): `DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, `DROPBOX_REFRESH_TOKEN` (long-lived; the SDK mints short-lived access tokens itself — never hardcode a short-lived token), `DROPBOX_TEMPLATE_ID` (printed once by `scripts/setup-dropbox-template.js` — re-running that script is safe, it detects and reuses an existing "FranVision Job" template rather than duplicating it). All Dropbox calls go through `dropbox-sync.js#getClient()`/`isConfigured()` — don't construct a second `Dropbox` client elsewhere. `dotenv.config()` is always called with `quiet:true` (dotenv 17.x otherwise prints a self-promotional console line on every load).

**`delivery-email.js`'s shared-link generation (`sharingCreateSharedLinkWithSettings`/`sharingListSharedLinks`) needs the app's OAuth token to carry the `sharing.write` scope** — unlike `dropbox-sync.js`'s/`file-sync.js`'s calls, which are all covered by `files.metadata.read/write` + `files.content.read/write`. If the "FranVision OS" app's current refresh token predates this feature, add `sharing.write` in the Dropbox App Console (App permissions tab) and re-run the OAuth flow to mint a new refresh token — until then, every link falls back to its placeholder token (best-effort, does not block job creation, but every link will be missing).

`scripts/check-job-properties.js <dropbox-path>` is a standalone debug utility — reads back a folder's hidden `jobId` property via the real API, useful for manually confirming a specific job's Dropbox state.

## Known limitations

- Push/Pull run synchronously within one HTTP request and return one final summary — no progress streaming for a large first-time sync of many/large files.
- The chunked-upload-session path (files >140MB) is unit-tested only against a fake client (exact byte-offset/sequence assertions) — never verified against a real 140MB+ file (deliberate, to avoid burning real time/bandwidth on an expensive test).
- **Editing an identity field (Shoot Date / Address / Client Name) of an already-created job makes a NEW job, not an edit.** Job identity IS `buildJobFolderName()`'s output (those 3 fields), so changing one changes the canonical name → no match → new folder + new Job ID; the old folder is orphaned and must be deleted by hand. Accepted limitation (see "Job Update" below and `DESIGN-job-update.md`). Everything else about a job IS editable in place — re-enter the same 3 fields and click Create Job (it becomes "Update FVS-…").
- No Windows support currently (macOS only) -- see "Running it" above.
- **All-in-One and Wave payment links in the Delivery Email are always manual fill-in** — no system generates either yet (see the "Delivery Email" decision above). Filling them in requires opening the generated `.txt` and editing it by hand; there's no UI field for it.
- **The Home Report line is effectively always included** until `folder-builder.js`'s unconditional Home Report folder creation is fixed to key off a real `order`/addon toggle — see the "Delivery Email" decision above.

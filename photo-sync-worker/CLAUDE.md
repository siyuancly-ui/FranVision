# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this directory (`photo-sync-worker/`). See the repo-root `CLAUDE.md` for how this module fits into the rest of FranVision. `DESIGN.md` (design + rationale) and `README.md` (ops runbook) alongside this file go deeper.

## What this is

A standalone **Cloudflare Worker** (`franvision-photo-sync`) that mirrors compressed thumbnails of the photos in Dropbox job folders into the **same Supabase project the Feature Sheet Builder uses**, so the (not-yet-built) Wix Gallery and the Feature Sheet Builder can display and pick from them without ever talking to Dropbox directly. It also mirrors job **videos** (the `Video`/`VLOG` sub-folders) into **Cloudflare Stream**, writing the resulting playback info into the same Supabase project's `projects.data.videos[]` — same "Dropbox is the only archive, Supabase is a display index" shape as photos.

- Originals stay in Dropbox and remain the only archive. Each synced photo record keeps a `dropboxFileId` pointing back to the high-res file for the future print/PDF path; each synced video record keeps a `dropboxFileId`/`dropboxPath` the same way.
- Supabase here is a **display cache + index**. Wiping Supabase Storage loses nothing permanent — re-run the backfill and every thumbnail regenerates. (Video re-encoding on Stream isn't covered by the photo backfill — see Known limitations.)
- It also writes a **larger delivery render back into Dropbox** (see "Two renders" below) — so unlike every other module, this Worker both reads *and writes* the studio's live Dropbox.

Independent service, its own repo-in-waiting: `photo-sync-worker/` is self-contained and can be split into its own GitHub repo later. It is **not** part of the Feature Sheet Builder despite sharing its Supabase project.

## Requires the Workers Paid plan

Cloudflare **Queues** (per-message retries + batching) and the higher subrequest limit are used — the free plan cannot run this. `wrangler.jsonc` declares the queue producer/consumer, a `*/2 * * * *` cron, and all non-secret vars.

## Running it

```bash
cd photo-sync-worker
npm install                     # devDependency: wrangler only (zero runtime deps)
cp .dev.vars.example .dev.vars  # fill in for local runs; prod uses `wrangler secret put`
npx wrangler dev                # local; GET / , GET /webhook?challenge=x , POST /admin/* work
```

Zero runtime dependencies — Dropbox and Supabase are both driven with raw `fetch`. ESM (`"type": "module"`).

## Tests

```bash
cd photo-sync-worker
npm test           # node --test, 102 cases, NO network
```

Pure helpers (`paths.js`, `photo-id.js`, `webhook.js`, the classify/collapse/group functions in `sync.js`) are unit-tested directly. The runners (`runDelta` / `processPhotoBatch` / `runBackfill`) take an injectable `deps` bag (`{ dbx, sb, enqueue, now }`) so tests hand in fake Dropbox/Supabase objects — the real API is never hit in tests. The video pipeline (`video-sync.js`) follows the same pattern with an extra fake `stream` object; see `test/video-sync.test.js`.

**Verifying anything beyond the fake-`deps` tests means running against the studio's real, live production Dropbox account AND the live Supabase project the Feature Sheet Builder uses.** Same rule as `job-generator/`: use an obviously-fake job name, and delete whatever you create (Dropbox folder, the `projects` row, its Storage objects) when done.

## Architecture: the pipeline

```
Dropbox change ─webhook (HMAC-verified)─┐
2-min cron (reconciliation) ────────────┤─▶ enqueue {type:"delta"} ─▶ Queue photo-sync-jobs
                                                                         │
   delta message: acquire lease lock in photo_sync_state, read cursor,   │
   files/list_folder/continue, collapse to last-state-per-path. The SAME  │
   collapsed entries are classified TWICE, independently:                │
     - photos: keep files/deletes under SYNC_FOLDERS, group by job,      │
       fan out one {type:"photo-batch", jobId, items} per job.           │
     - videos: keep files/deletes under VIDEO_SYNC_FOLDERS, group by     │
       job, fan out one {type:"video-batch", jobId, items} per job.      │
   Both resolve the hidden jobId property per folder (skip untagged,     │
   shared cache), then the cursor advances. ───────────────────────────┤
                                                                         ▼
   photo-batch message, per job:
     1. get_thumbnail_batch(THUMB_SIZE=w1024h768) -> Supabase Storage
        photos/<jobId>/<photoId>_thumb.jpg  +  photos_upsert() RPC into projects.data.photos[]
     2. (MLS only) second get_thumbnail_batch(DOWNLOAD_THUMB_SIZE=w2048h1536)
        -> files/upload to <jobFolder>/MLS for download/<name>.jpg   (best-effort)
     deletes -> photos_mark_pending() + delete the MLS-for-download copy

   video-batch message, per job:
     1. files/get_temporary_link -> Cloudflare Stream "copy from URL"
        (Stream fetches the Dropbox file itself, async; Worker never
        proxies video bytes) -> videos_upsert() RPC, status:"processing"
        + one row in video_sync_pending
     deletes -> videos_mark_pending() (Stream object itself not freed yet)

2-min cron ALSO enqueues {type:"video-poll"} -> for each video_sync_pending
row, check Stream's encode status; readyToStream -> videos_upsert() with
status:"ok" + playbackUrl/thumbnailUrl, row removed; Stream-reported error ->
status:"error", row removed; still encoding -> left for the next tick.

2-min cron ALSO enqueues {type:"render-retry-poll"} -> for each
photo_render_pending row (a delivery-copy or large-render that failed in a
photo-batch run above), retry it; success deletes the row, failure bumps
attempts/last_error, MAX_RENDER_RETRY_ATTEMPTS (20) abandons + deletes it.
```

### What it adds to the shared Supabase project (`papaswihicvajzcubbri`, the Feature Sheet Builder's)

- **`photo_sync_state`** table — one row (`id='default'`): the Dropbox `list_folder` cursor + a `locked_until` lease lock. No `anon` access.
- **`photos_upsert(p_project_id, p_photo jsonb)`** — atomic merge of one photo into `projects.data.photos[]`: creates the row if missing, `SELECT … FOR UPDATE` serializes concurrent writers (this Worker's own batches AND a human in the Feature Sheet Builder), matches by `photoId`, shallow-merges so Feature-Sheet-Builder-owned keys (`role`, sort order, …) survive.
- **`photos_mark_pending(p_project_id, p_photo_id)`** — flag one photo `status:"pending_review"`, remove nothing.
- New keys the Worker writes on each `projects.data.photos[]` entry: `photoId`, `filename`, `width`, `height`, `hasThumb`, `dropboxFileId`, `dropboxPath`, `dropboxRev`, `folder`, `status`, `syncedAt`, and (MLS only) `downloadDropboxPath`. Storage bucket + path rule are unchanged from the Feature Sheet Builder: `photos/<jobId>/<photoId>_thumb.jpg`.
- **`video_sync_pending`** table — one row per video awaiting Cloudflare Stream encoding (`project_id`, `video_id`, `stream_uid`), polled and deleted once finalized. No `anon` access.
- **`videos_upsert(p_project_id, p_video jsonb)`** / **`videos_mark_pending(p_project_id, p_video_id)`** — same shape as the photo functions above, targeting `projects.data.videos[]` matched by `videoId`.
- Keys the Worker writes on each `projects.data.videos[]` entry: `videoId`, `filename`, `folder`, `dropboxFileId`, `dropboxPath`, `dropboxRev`, `streamUid`, `status` (`processing`/`ok`/`error`/`pending_review`), `syncedAt`, and once ready: `durationSec`, `playbackUrl`, `thumbnailUrl`. No Storage bucket involved — the encoded video lives in Cloudflare Stream, not Supabase Storage.
- **`photo_render_pending`** table (2026-09-16) — one row per delivery-copy (`kind:'download_copy'`) or large-render (`kind:'large'`) that failed in `processPhotoBatch`, auto-retried by the 2-min cron's `render-retry-poll` until it succeeds or hits `MAX_RENDER_RETRY_ATTEMPTS`. Unique on `(project_id, kind, source_path)` so repeat failures before the next poll merge into one row instead of piling up. No `anon` access, no RPC — plain PostgREST insert/list/update/delete from `src/supabase.js`.

## Confirmed design decisions (several were the road not taken first — re-read before "fixing")

- **No Cloudflare Image Resizing / no WASM. Dropbox does all image work.** Thumbnails come from Dropbox's own `get_thumbnail_batch` (25/call) with `get_thumbnail_v2` as a per-file fallback. The `fetch(..., {cf:{image}})` path was rejected: it needs a zone + a specific plan and *silently returns the original* when unavailable. The Worker never decodes or resizes an image itself.
- **Two renders per MLS photo, each fit for purpose.** `THUMB_SIZE` (`w1024h768`) → Supabase, for Gallery / Feature Sheet Builder *display and selection*. `DOWNLOAD_THUMB_SIZE` (`w2048h1536`, Dropbox's largest; a 3:2 landscape → 2048×1365, ~0.4–0.9 MB) → written back into Dropbox `<job>/MLS for download/` as the human-downloadable *delivery* set. Franky judged 1024 too soft for MLS delivery (2026-09-08). `w2048h1536` on the *batch* endpoint is not 100% confirmed in production — the `get_thumbnail_v2` fallback covers it if a batch entry fails.
- **`photoId` is path-derived, NOT the Dropbox file id.** `hash(jobId + '/' + relPathFromJob)`. A delete + re-upload of the same name produces a *new* Dropbox file id but the *same* path → same `photoId` → the self-heal falls out for free. A pure rename changes the path and thus the id (treated as delete+add — acceptable, renames are rare).
- **Self-heal (implemented + end-to-end verified 2026-09-08).** Dropbox delete → `status:"pending_review"` on the record (nothing removed) + the `MLS for download` copy is hard-deleted (pure derivative). A same-name re-upload lands on the same `photoId` → `photos_upsert` flips it back to `"ok"`, rebuilds the delivery copy, logs `photo_healed`. A different name leaves the old record `pending_review` for a human. There is no filename-fuzzy-matching — it is exact same relative path.
- **`SYNC_FOLDERS` = `MLS, HDR Photos, Virtual Staging, Floorplan, Local Report, Cover&Closing, Callout`.** Only web-image extensions (`.jpg/.jpeg/.png/.webp`) under these sub-folders of a tagged job folder are synced. `0 RAW`, `Home Report`, videos, PDFs, `MLS for download` itself (loop guard) are all ignored. `DOWNLOAD_SET_FOLDERS` = `MLS, HDR Photos`. Both `MLS` and `HDR Photos` are listed because Job Generator renamed its `MLS` folder to `HDR Photos` on 2026-09-12 (pure naming change) — pre-rename jobs still have a real `MLS` folder on Dropbox, new jobs use `HDR Photos`; both need to keep syncing. (This was briefly broken 2026-09-08→2026-09-14: the deployed config only listed `MLS`, so every post-rename job's main photos silently never synced — fixed in commit `16e8562`, verify against the live `wrangler.jsonc`/`GET /admin/status` rather than trusting this doc if something seems off again.) **`Cover&Closing` / `Callout` (2026-09-15, `Cover`+`Closing` merged into one folder 2026-09-17) are delivery-page's manual-override folders** — Job Generator doesn't create these by default yet (deferred on purpose, see [[franvision-delivery-page]]), so they only ever get anything in them if a human manually creates the folder in Dropbox and drops photo(s) in — this Worker doesn't care either way, it syncs whatever's there under these names exactly like any other folder.
- **A recognized folder can be nested inside another one, not just directly under the job folder (confirmed 2026-09-16)** — e.g. `Callout` living at `<job>/HDR Photos/Callout/x.jpg` rather than `<job>/Callout/x.jpg`. `paths.js#parseJobPath` now returns `ancestors` (every directory name between the job folder and the file); `matchAncestorFolder(ancestors, list)` scans INNERMOST-first so the most specific match wins (e.g. `Callout` over the outer `HDR Photos`), and `classifyForSync`/`classifyForVideoSync` use that matched name — not always `parsed.subFolder` — as the `folder` value written to Supabase. Fully backward compatible: a plain, non-nested file only ever has one ancestor, so existing behavior for every current flat folder is unchanged; an unrecognized inner folder (e.g. a photographer's own `HDR Photos/Retouched/x.jpg` organizing habit) falls through to the outer recognized folder exactly as before.
- **`DROPBOX_JOBS_ROOT=""`** — the Dropbox app is Full Dropbox and Job Generator creates job folders at the account root. If jobs ever move under one parent folder, set this var to that path; no code change.
- **Webhook responds 200 immediately; all work is in the queue.** Dropbox webhooks carry no change list — the Worker keeps a recursive `list_folder` cursor in `photo_sync_state` and diffs on each run. The lease lock makes delta runs serial (concurrent/duplicate webhooks that can't take the lease just `ack` after logging `delta_skipped_locked`).
- **Idempotent throughout.** Delta collapsed to last-state-per-path; `projects` writes via the atomic RPC keyed on `photoId`; Storage upload is `x-upsert`; delivery copy is `mode:overwrite` at a deterministic path.
- **Best-effort layering.** A single bad photo is logged (`thumb_skip` / `photo_error`) and skipped, never sinking the batch. The delivery-copy and large-render passes are best-effort (`download_copy_failed` / `delivery_batch_failed` / `large_render_failed` / `large_batch_failed`) — the Gallery record is already saved, and a failure queues a `photo_render_pending` row for the 2-min cron to auto-retry (see below) rather than waiting on a human to notice and re-run backfill. Only a whole-batch infra failure (`get_thumbnail_batch` throws, Supabase down) throws, so the Queue message retries with backoff; after `max_retries: 5` it lands in `photo-sync-dlq`.
- **A same-batch photo replacement under a DIFFERENT extension no longer wipes out its own new delivery copy (fixed 2026-09-16).** `downloadCopyPath()` strips the source extension and always appends `.jpg`, so `a.jpg` and `a.jpeg` both normalize to the SAME `MLS for download/a.jpg` destination. Root cause of the 48 Red Ash Dr gap this doc's other 2026-09-16 entries describe: a photo was replaced by deleting the old file and dragging in a new one under a different extension, producing an upsert (new file) and a delete (old file) in the SAME photo-batch message — `processPhotoBatch` runs the delivery-copy pass for upserts BEFORE the deletes loop, so the delete's cleanup (intended to remove the OLD file's now-stale copy) actually removed the replacement's brand new copy that had just been written to that identical path. Fixed by tracking every path the delivery-copy pass actually wrote in that batch (`deliveredDestPaths`) and skipping the delete-cleanup for any delete whose target matches one (`download_copy_delete_skipped_same_batch_replacement`) — a genuine standalone deletion (no same-batch replacement) still drops its copy exactly as before.
- **`HDR Photos/Callout/` gets a download copy too, mirrored as `MLS for download/Callout/` (2026-09-23).** `DOWNLOAD_NESTED_FOLDERS` (`Callout`) names folders that count only when nested UNDER a `DOWNLOAD_SET_FOLDERS` folder; `paths.js#downloadSubdirFor` returns the sub-directory (`''` flat for HDR Photos/MLS files, `Callout` for the nested one, `null` = no copy) and `downloadCopyPath(..., subdir)` builds the mirrored path. A job-level `Callout/` (delivery page's aerial curation) still gets no copy. Delete/self-heal/retry follow the same path. Existing jobs need `POST /admin/backfill` once to generate their Callout copies.
- **A genuine Dropbox-side delete of a photo in a `DOWNLOAD_SET_FOLDERS` folder (MLS/HDR Photos) DOES delete its `MLS for download` copy too** — this is intentional (the copy is a pure derivative of a file that no longer exists) and unaffected by the fix above, which only skips the delete when a same-batch upsert just recreated that exact path.
- **Delivery-copy/large-render failures auto-retry via `photo_render_pending` + the 2-min cron (2026-09-16), not just on the next manual backfill.** Found in real use TWICE (186 Test Dr missing 5 MLS-for-download files, then 48 Red Ash Dr missing 3) that the old "best-effort, next backfill picks it up" story meant nobody actually noticed or re-ran backfill — the gap just sat there indefinitely. Now every `download_copy_failed`/`large_render_failed` inserts a row (`sb.insertPendingRender`, merge-duplicates on `(project_id, kind, source_path)`), and `processRenderRetryPoll` (dispatched by the same cron tick as `video-poll`, message type `render-retry-poll`) retries each one with a single `get_thumbnail_v2` call: success deletes the row (`render_retry_succeeded`), failure bumps `attempts`/`last_error` (`render_retry_failed`), and a row that's failed `MAX_RENDER_RETRY_ATTEMPTS` (20) times is deleted and abandoned (`render_retry_abandoned`) rather than retried forever — a persistently-failing source (e.g. deleted from Dropbox in the meantime) shouldn't retry every 2 minutes indefinitely. Deliberately does its own single-file fetch rather than reusing `processPhotoBatch`'s batch path — pending rows are expected to be sparse, so simplicity won over batching efficiency here. `POST /admin/backfill` still exists for a full manual re-sweep (e.g. after changing `DOWNLOAD_THUMB_SIZE`), but is no longer the only way a dropped render gets fixed.
- **`LARGE_THUMB_FOLDERS` = `Cover&Closing, Callout, Local Report, Floorplan` (2026-09-15, folder name updated 2026-09-17, `Floorplan` added 2026-09-18 alongside delivery-page's new Floor Plan section), a second render for [[franvision-delivery-page]]'s full-bleed sections.** Every `processPhotoBatch` upsert whose `subFolder` matches this list gets a SECOND `get_thumbnail_batch` call at `DOWNLOAD_THUMB_SIZE` (reusing the existing w2048h1536 config, same as the Dropbox delivery-copy render — independent pass, own batch/fallback, not shared bytes) uploaded to Supabase Storage as `<photoId>_large.jpg` (`sb.uploadLarge`), then a follow-up `photos_upsert` merges `hasLarge:true` onto the already-saved record. **Deliberately NOT applied to the whole main gallery (`MLS`/`HDR Photos`)** — those stay small-only (`THUMB_SIZE`/`_thumb.jpg`) to avoid inflating storage and Feature-Sheet-Builder-picker load time for every synced photo. Entirely best-effort (`large_batch_failed`/`large_render_failed`), never blocks the small thumb or the rest of the batch.
- **`ORIGINAL_RENDER_FOLDERS` = `Floorplan` (2026-09-18) -- a subset of `LARGE_THUMB_FOLDERS` that gets the TRUE original file bytes instead of a Dropbox-thumbnail-API render.** A floor plan export is already small (a diagram/screenshot, not a DSLR photo), so a `w2048h1536` derivative just adds JPEG re-compression -- and re-encodes it as JPEG even if the source was a PNG -- for no real size benefit; the true original is both smaller in bytes AND sharper for text/lines. `dbx.downloadFile(path)` (Dropbox's plain `files/download` content endpoint, no `format`/`size`/`mode` args at all, unlike `get_thumbnail_batch`/`get_thumbnail_v2`) fetches the exact bytes; `paths.js#imageContentType(filename)` maps the real extension to a Content-Type (defaults to `image/jpeg` for anything unrecognized) passed to `sb.uploadLarge(..., contentType)`. **The Storage object key still always ends in `_large.jpg` regardless of the real format** -- delivery-page's URL builder assumes that suffix universally, and browsers render from the `Content-Type` header + sniffed bytes, not the URL's extension, so a PNG served at a `.jpg`-suffixed path is harmless. Every other `LARGE_THUMB_FOLDERS` folder is deliberately left off this list -- a real estate photo's true original can be tens of MB, exactly what the `w2048h1536` cap exists to avoid; only add a folder here when its source files are known to already be small. Not worth batching (one `downloadFile` call per item -- there's no batch-original endpoint). `processRenderRetryPoll`'s retry path re-derives whether a pending `'large'` row is an original-render one from `source_path` itself (`matchAncestorFolder` against `originalRenderFolders`) rather than storing that on the row -- one less thing that could drift out of sync with the row's actual folder.
- **Gallery hero/closing fallback ALSO gets a large render, but scoped to just the (at most two) photos that fallback actually picks (2026-09-17), not the whole gallery.** When a Job has no `Cover&Closing` override, delivery-page's hero/closing sections fall back to the 3rd/5th gallery photo by filename (see delivery-page/CLAUDE.md) — before this, that fallback stayed on the small `_thumb.jpg` forever, since main-gallery photos never got `hasLarge:true`. `pickGalleryFallbackTargets()` (pure, mirrors delivery-page's `pickPhotos`/`fallbackPhoto`/dedup logic exactly) re-derives which 1-2 photos those would be from the CURRENT full gallery (`sb.getProjectPhotos`, not just this batch's items, since an earlier batch's photo can be the one that needs it) whenever a batch touches a gallery-folder item (upsert OR delete), and large-renders only those via the existing single-file `get_thumbnail_v2` path (no need for batching — at most 2 photos). Reuses `photo_render_pending` on failure exactly like the other large-render pass. A stale `hasLarge:true` left on a photo that's no longer 3rd/5th (because new photos shifted the pick) is never cleared — harmless unused Storage, not worth the complexity of tracking/removing.
- **Interim address sync into `projects.data.address` (2026-09-15), for [[franvision-delivery-page]].** Every `processPhotoBatch` call best-effort parses the Dropbox job folder name (`"YYYY.M.D Address_Client"`, job-generator's `sanitize.js#buildJobFolderName()` format — `paths.js#parseAddressFromJobFolder` is its inverse) and, if it matches, writes `{address}` via the shared `project_set_delivery_info()` RPC (owned by `delivery-page/supabase/schema.sql`, not this module's own schema.sql — same Supabase project, reused rather than duplicated). Idempotent overwrite, wrapped in try/catch (`address_sync_failed` on error), never blocks the actual photo sync below it. **This is explicitly a transitional hack**, not the real design — job-generator's `job.json` is local-only and never reaches Supabase today, so this is the only address source available without a bigger integration. Once job-generator itself moves online and can push `job.json` fields (including `address`) directly, this folder-name-parsing should be retired in favor of that, not extended further (e.g. don't also start parsing client name or other fields out of the folder name — ask before doing more of this).
- **Floor Tour / 3D Tour link sync via a single well-known Dropbox text file (2026-09-16), same "no data entry, just a file" shape as `Cover&Closing`/`Callout`/`Local Report`.** A human drops one `Tour Link.txt` file (name configurable via `TOUR_LINK_FILENAME`, default `"Tour Link.txt"`) directly at a job folder's ROOT (not nested in any sub-folder -- `paths.js#isTourLinkCandidate` requires `depth === 2`) containing just the URL as plain text. `tour-link-sync.js` (a third pipeline parallel to `sync.js`/`video-sync.js`, wired into both `runDelta` and `runBackfill` exactly like the video pipeline) downloads the file's text (`dbx.downloadText`, a new small content-download method) and writes it as `tourUrl` via the shared `project_set_delivery_info()` RPC; a delete clears `tourUrl` back to `null`. **Deliberately does NOT set `tourType`** -- delivery-page's `tourHtml()` renders Floor Tour and 3D Tour identically (same iframe slot, no per-provider markup difference), so there is nothing for a filename/type distinction to encode; a single generic file/field covers both. Rejected an earlier idea of adding a form field to Job Generator for this: by the time a delivery page is being assembled, staff are no longer in Job Generator's workflow at all, so a field there doesn't fit how the link actually gets known/entered.
- **`width`/`height`** come from the delta entry's `media_info`; Dropbox generates that asynchronously after upload, so when it's missing the Worker does one `get_metadata(include_media_info)` refetch, and still tolerates `null`.
- **Backfill is manual and cursor-independent.** `POST /admin/backfill` (bearer `ADMIN_TOKEN`), empty body = all tagged jobs, `{"jobId":"FVS-…"}` = one. Not run on deploy. Use it to seed pre-existing jobs, or to re-generate every delivery copy after changing `DOWNLOAD_THUMB_SIZE`. Walks both `SYNC_FOLDERS` (photos) and `VIDEO_SYNC_FOLDERS` (video) off the same walked file list, dispatching `photo-batch` and `video-batch` messages respectively.
- **Video host: Cloudflare Stream, not Vimeo/YouTube.** Chosen for cost (duration-based pricing, not GB-based — resolution/bitrate don't move the price) and because it's the same Cloudflare account/API surface this Worker already uses, minimizing integration work. See the project's conversation history for the full comparison.
- **Video sync is additive and parallel to the photo pipeline, not merged into it.** `video-sync.js` is a separate file from `sync.js`; `runDelta` classifies the same collapsed delta entries twice (once per pipeline) and dispatches a separate `video-batch` message type. Deliberate: the already-shipped, acceptance-tested photo flow is never touched by video changes.
- **No proxying of video bytes through the Worker.** Cloudflare Stream's "copy from URL" (`POST /stream/copy`) lets Stream fetch the source itself, async. The Worker only needs a short-lived direct-download URL for the Dropbox file (`files/get_temporary_link`, ~4h validity) — multi-GB 4K files never touch the Worker's CPU/memory/body-size limits.
- **Video encoding completion is polled, not pushed via a Stream webhook.** A `video_sync_pending` table (one row per in-flight upload) is checked by the existing 2-min cron (`{type:"video-poll"}`, alongside the existing `{type:"delta"}`). Simpler than adding a second signed-webhook scheme; consistent with how this Worker already treats Dropbox itself as "poll on a timer, webhook is just a wake-up hint."
- **`videoId` reuses the exact same derivation as `photoId`** (`hash(jobId + '/' + relPathFromJob)`, imported under a local alias) — no separate hashing logic, and the same self-heal property falls out: delete + same-name re-upload keeps the same `videoId`, though note it goes through a **fresh Stream upload** (new `streamUid`) since the old Stream video isn't reused.
- **A Dropbox-side video delete frees the Cloudflare Stream copy.** Before flagging `pending_review`, `processVideoBatch` reads back the existing record via `sb.getProjectVideo` and best-effort calls `stream.deleteVideo(streamUid)` — a Stream failure here never blocks the Supabase `pending_review` write (logged as `video_stream_delete_failed`).

## Environment / secrets

Set with `wrangler secret put` (never a committed file; `.dev.vars` is gitignored, `.dev.vars.example` documents the list):
`DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, `DROPBOX_REFRESH_TOKEN` (the **same** three the Job Generator uses — same "FranVision OS" app, Full Dropbox; the token needs `files.metadata.read/write` + `files.content.read/write`, which cover the File Properties API too — there is no separate `file_properties` scope), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (service-role — bypasses RLS), `ADMIN_TOKEN` (guards `/admin/*`), `CF_STREAM_API_TOKEN` (needs Stream:Edit permission on the account named by `CF_ACCOUNT_ID`), `RENDER_TOKEN` (bearer for `GET /render/...`; same value as the Feature Sheet Builder's admin token).
Non-secret config is `vars` in `wrangler.jsonc`: `DROPBOX_JOBS_ROOT`, `SYNC_FOLDERS`, `VIDEO_SYNC_FOLDERS` (default `Video,VLOG`), `TOUR_LINK_FILENAME` (default `Tour Link.txt`), `THUMB_SIZE`, `DOWNLOAD_THUMB_SIZE`, `DROPBOX_TEMPLATE_ID` (`ptid:R599LCPosWEAAAAAAAAIFA`, the shared jobId PropertyGroupTemplate), `DOWNLOAD_SET_FOLDERS`, `DOWNLOAD_SUBFOLDER`, `MAX_DELTA_ENTRIES_PER_RUN`, `CF_ACCOUNT_ID` (not sensitive, but paired with the `CF_STREAM_API_TOKEN` secret above).

## Known limitations

- **A `w2048h1536` batch response has not been confirmed in production.** If Dropbox rejects it per-entry the code falls back to `get_thumbnail_v2` one file at a time (more subrequests, fine on paid) — but if the *whole* batch endpoint rejects the size, watch for `delivery_batch_failed` then per-file fallbacks in `wrangler tail` on the first real MLS batch.
- **Old delivery copies are not auto-upgraded** when `DOWNLOAD_THUMB_SIZE` changes — run `POST /admin/backfill` (all or per-job) to re-render them.
- **Webhook storm during a photographer's bulk upload**: every changed file fires a webhook → many cheap `delta_done` runs (mostly `entries:0`, most changes land in `0 RAW` and are filtered out). Harmless and keeps up in real time; there is deliberately **no debounce** yet.
- **A queued `photo-batch` message lost after the cursor advanced** is not recovered by the cron (which resumes from the advanced cursor) — it relies on Cloudflare Queues' at-least-once delivery, with `POST /admin/backfill` as the manual repair. Low risk; noted.
- **No retention/cleanup** for the Supabase free tier (1 GB) yet — a cron to drop thumbnails + `pending_review` rows for jobs older than N months is a future item (originals are safe in Dropbox; backfill rebuilds).
- **`pending_review` has no human-facing surface yet** — it's a field in `projects.data.photos[]`/`projects.data.videos[]`; showing it is a Gallery / Feature Sheet Builder UI concern.
- **3D tours are out of scope by design** — inserted as a manual external link (e.g. Matterport), not sourced from Dropbox at all; no code here can or should touch them.

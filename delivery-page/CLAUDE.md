# CLAUDE.md

This file provides guidance to Claude Code when working in this directory (`delivery-page/`). See the repo-root `CLAUDE.md` for how this module fits into the rest of FranVision, and `franvision-delivery-page-design-spec.md` (repo root) for the target visual design this module is working toward.

## What this is

A standalone **Cloudflare Worker** (`franvision-delivery-page`) that renders the client-facing per-Job delivery page at `/delivery/<jobId>`, reading the **same Supabase project** [[photo-sync-worker]] writes to. It is read-mostly: photos/videos are entirely photo-sync-worker's to write; this Worker only writes the small set of delivery-specific fields (`address`, `tourUrl`, `tourType`) via its own admin endpoint.

Independent service, own repo-in-waiting, same shape as `photo-sync-worker/` — self-contained, free Cloudflare plan (no Queues, no cron).

## Running it

```bash
cd delivery-page
npm install                     # devDependency: wrangler only, zero runtime deps
cp .dev.vars.example .dev.vars  # fill in with the SAME SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY
                                 # photo-sync-worker/.dev.vars uses, plus a new ADMIN_TOKEN
npx wrangler dev                # GET /, GET /delivery/<jobId> or /<slug>/<jobId>, GET /delivery/<slug>/<token> (Gallery), GET /admin, POST /admin/jobs/<jobId>
```

## Tests

```bash
cd delivery-page
npm test    # node --test, 83 cases, NO network
```

`src/render.js` is pure (`buildDeliveryModel` shapes a Supabase `projects` row into a template model; `renderDeliveryPage`/`renderNotFoundPage` are string-building functions) — fully unit-tested without touching Supabase. `src/index.js` (the Worker's `fetch` handler) and `src/supabase.js` (raw-fetch client) are thin and untested directly, same division of labor as photo-sync-worker.

## Deploy

```bash
cd delivery-page
npx wrangler secret put SUPABASE_URL              # + SUPABASE_SERVICE_ROLE_KEY, ADMIN_TOKEN
npx wrangler deploy
# supabase/schema.sql (project_set_delivery_info()) already applied in the
# SQL editor as of 2026-09-15 -- no need to re-run unless working against a
# different Supabase project.
```

### Custom domain: `realgta.ca` (registered + bound 2026-09-17, supersedes the abandoned `real.gta3d.ca` plan)

**The `real.gta3d.ca` subdomain-delegation plan is dead — do not attempt it.** It looked correct on paper (Cloudflare's own docs confirm "delegate a subdomain to Cloudflare while the parent domain stays on a different DNS provider" is a real, supported pattern) but Cloudflare's dashboard "Add a site" flow rejects it outright with "Please ensure you are providing the root domain and not any subdomains" — hit that exact error 2026-09-17. It may still be possible via Cloudflare's API or support, but wasn't pursued once a simpler option existed.

**What was done instead: registered a brand-new root domain, `realgta.ca`, directly through Cloudflare Registrar** ($9.19/year, no markup, confirmed available via direct CIRA WHOIS before buying). Registering through Cloudflare Registrar makes Cloudflare the DNS authority automatically — no delegation dance, and `gta3d.ca`'s existing DNS surface (Wix's own site, Zenfolio's `realimage(s).gta3d.ca`, a large number of legacy per-listing subdomains, MX/email) stays completely untouched, since it's not being used for this at all anymore.

Bound as the **root domain**, no subdomain prefix (Cloudflare dashboard → `franvision-delivery-page` Worker → Domains → Add Domain → `realgta.ca`, subdomain field left blank). **Live at `https://realgta.ca`**, both URL shapes work (see Architecture below for the pretty-URL format, added 2026-09-17).

**Feature Sheet Builder is NOT a usable template for domain setups in this repo** — checked directly (2026-09-16): the `franvision` Worker (FSB) had no Cloudflare Custom Domain bound at that time (it has since been bound to `fs.realgta.ca`, 2026-09-21).

## Architecture

```
GET /delivery/<jobId>            -- original path, still works
GET /<address-slug>/<jobId>      -- pretty path (2026-09-17), e.g.
                                     /1371-kestell-blvd-oakville/FVS-20260917-003
  Both -> supabase.getProject(jobId)         (raw fetch, service-role key --
                                               the address-slug segment is
                                               NEVER inspected, purely
                                               cosmetic; only the jobId
                                               segment does the lookup)
       -> render.buildDeliveryModel(project, ...) (pure: pick hero/gallery/closing
                                               photos, video, tour, local report)
       -> render.renderDeliveryPage(model)        (pure: HTML string, sections
                                               omitted when their data is absent)

POST /admin/jobs/<jobId>   (bearer ADMIN_TOKEN)
  body: { address?, tourUrl?, tourType? }
  -> supabase.setDeliveryInfo(jobId, fields) -> project_set_delivery_info() RPC
     (merges into projects.data, creates the row if it doesn't exist yet)

GET /admin?admin=<ADMIN_TOKEN>
  -> supabase.listProjects()          (every projects row, newest-updated first)
  -> admin.buildAdminModel(rows)      (pure: address/agents/photoCount/hasVideo/hasTour per
                                        Job, sorted like FSB's admin -- see below)
  -> admin.renderAdminPage(model)     (pure: HTML directory table, client-side filter)
```

### Module map

| File | Role |
|---|---|
| `src/index.js` | Worker `fetch` handler: routes `GET /`, `GET /delivery/<jobId>`, `GET /<address-slug>/<jobId>`, `GET /admin`, `POST /admin/jobs/<jobId>` |
| `src/supabase.js` | Raw-fetch client: `getProject(jobId)` (read-only), `listProjects()` (read-only, admin directory), `setDeliveryInfo(jobId, fields)` (the one write this Worker does), generic `rpc()` |
| `src/render.js` | All pure logic: photo/video/tour selection (`buildDeliveryModel`), HTML template (`renderDeliveryPage`, `renderNotFoundPage`), `escapeHtml`, `slugifyAddress`/`deliveryPath` (pretty-URL builder) |
| `src/gallery.js` | The standalone Gallery page (2026-09-24): `isGalleryToken`/`galleryPath`, `buildGalleryModel`, `renderGalleryPage` (hero + 2 ZIP buttons + masonry + lightbox), `zipFilename` |
| `src/admin.js` | Pure logic for the admin directory: `buildAdminModel(rows)`, `renderAdminPage(model, {origin})` (imports `escapeHtml` from `render.js`) |
| `supabase/schema.sql` | Run once — adds `project_set_delivery_info()` |

## Confirmed design decisions

- **Admin directory at `GET /admin?admin=<ADMIN_TOKEN>` (2026-09-17), same query-param-token shape as Feature Sheet Builder's own admin page** — a bookmarkable-but-secret link Franky keeps, not a curl-only bearer endpoint like `POST /admin/jobs/<jobId>` above. Lists every `projects` row with address, agent(s), photo count, video/tour presence, updated time, and a "Copy agent link" button (writes the full absolute delivery-page URL to the clipboard via `render.js#deliveryPath` — the pretty `/<address-slug>/<jobId>` form when an address is known, else `/delivery/<jobId>` — `navigator.clipboard.writeText` + a `prompt()` fallback — same pattern as FSB admin.js's own copy-link button); a plain client-side filter box, no build step. **Deliberately read-only, no create/duplicate/delete/recycle-bin unlike FSB's admin** — a delivery page exists because a Job exists, it isn't a separate thing to manage the lifecycle of from here.
- **Delivery Hub page (2026-09-25, branch `delivery-hub`, NOT yet deployed/merged): `/deliver/<address-slug>/<token>[/go/<KEY>]` (`src/hub.js`).** The payment gate. What the Delivery Email links to for everything below its "-----" line: one button per deliverable, the SAME set `job-generator/delivery-email.js#getDeliverableLines()` produced (HDR, MLS, VIDEO, FLOORPLAN, THREE_D, LOCAL_REPORT, HOME_REPORT; only the ones this Job has), stored per Job in the `delivery_hub` table (`job-generator/supabase/delivery-hub.sql`, written by Job Generator's `jg_delivery_hub()` RPC at Create/Update Job together with the Wave payment link + invoice total). Unpaid: a click opens a short "please pay to unlock" dialog (amount + two buttons: **Pay by credit card** -> Wave `viewUrl` in a new tab, hidden when the Job has no Wave link; **Pay by e-Transfer** -> a small panel with the EMT address, Copy button and "tell Franky / send a screenshot"; **no manual refresh**: once the dialog has been opened the page polls `GET /deliver/<slug>/<token>/status` (`{unlocked}`, no-store) every 5s and on tab focus, and the moment the Job is paid/unlocked it navigates to the hub itself, now unlocked -- so a client who pays in the other tab just comes back to a page that has already unlocked. Wave's pay page cannot send the client back to us (no return-URL setting known), which is why the old tab unlocks itself instead). `paid` OR `unlocked` (Franky's "deliver first, pay later" switch): the same button goes straight to the target **in a NEW TAB** (`target=_blank`), so the hub stays open and there's no Back button to press. **The gate is server-side**: a locked button is rendered with NO target, `/go/<KEY>` re-checks paid/unlocked on every hit (locked -> re-renders the hub with the dialog open, never a redirect), and the locked HTML contains no Dropbox link/Gallery token (unit-tested). Targets: HDR -> the Gallery page (`/delivery/<slug>/<gallery token>`, unchanged, still ungated by itself -- its random token is the secret, so it must never go in the email any more), THREE_D -> `projects.data.tourUrl` (= the text of the job's Dropbox `Tour Link.txt`, synced by photo-sync-worker's `tour-link-sync.js` -- the interim source until an API returns the tour URL to our database; read at click time, so editing the txt updates the button; only the first non-empty line is used, and it must be an http(s) URL), the rest -> the Dropbox shared link stored in the row (302 redirect; **not proxied, so the Dropbox URL is visible after the click** -- proxying through the Worker is a later option). MLS deliberately stays a Dropbox link, same as the old email (user 2026-09-25). The All in One page stays public; the hub only links to it. A button whose target isn't ready yet (no tourUrl / no link) shows "Preparing…". The hub has its OWN token (not the Gallery's) so the Gallery URL stays unknown to unpaid clients. Wrong/malformed token = the same 404 as a missing Job.
  - **Wave credit-card payments unlock automatically via Wave's webhook (2026-09-25, built, not yet enabled in Wave): `POST /webhooks/wave` (`src/wave-webhook.js`).** Facts verified from Wave's official Webhooks Setup Guide (see the `wave-webhooks-verified-facts` memory): Pro plan; headers `x-wave-signature: t=<s>,v1=<hex>`, signed string `<t>.<raw body>`, HMAC-SHA256 with the webhook secret, timestamp within 5 min; payload `{event_id, event_type, business_id, data:{invoice_id, amount_paid, remaining_balance, paid_date, ...}}`. Secret = Worker secret `WAVE_WEBHOOK_SECRET` (**no Wave API token is needed on the Worker**). The event's `invoice_id` is the numeric part of the GraphQL invoice id (`Business:<uuid>;Invoice:<n>`, 19 digits -> always a string), which Job Generator stores as `delivery_hub.wave_invoice_id` (`job-backend.js#waveInvoiceNumber`). Rules (user, 2026-09-25): **only a FULLY paid invoice unlocks** (`invoice.paid`/`invoice.overpaid` with remaining balance <= 0) -> `paid=true, paid_source='wave'`; `invoice.partially_paid` (or a "paid" event that still shows a balance) only records `wave_paid_cents`/`wave_remaining_cents` and `/admin` shows an orange "部分付款 Partial: 已付 $X, 还差 $Y" hint, **Paid stays unticked**; the hub page shows an orange "Paid $X, $Y more to unlock downloads. / 已付 $X，还需支付 $Y 才能解锁下载。" note and the pay dialog asks for the remainder (a safety net only -- partial payments are rare for Franky; `/status` also returns `remainingCents` so an open page refreshes itself after a partial payment). In `/admin` a Wave-paid Job's Paid box is **ticked, greyed-out and disabled, and the server refuses to untick it (409)** -- that alone tells Franky it was Wave, not his own e-Transfer tick (manual ticks stay editable, `paid_source='manual'`). e-Transfer is still confirmed by Franky by hand until the reconciliation assistant exists. Every delivery is stored once in `wave_events` (event_id = dedupe key; Wave retries; `result` = paid / partial / no matching job / ignored), the audit trail for unmatched events; the route answers 200 for everything after a valid signature (Wave disables a subscription after 10 consecutive failures) and 401 only for a bad signature. **Wave webhook is REGISTERED (2026-09-25):** Wave app `FranVision Invoicing Automation` (id 19630 -- the existing app behind the API token, so no new app / OAuth consent was needed), subscription `0a856e95-e908-415b-9d7c-239b0f0f25da`, status ACTIVE, events invoice.paid / invoice.partially_paid / invoice.overpaid, **endpoint = `https://franvision-delivery-page.frankystudio-6f3.workers.dev/webhooks/wave` (the workers.dev URL, NOT realgta.ca)**. Why: Wave validates the URL when you press Save (server-side Python client from Google Cloud) and only then shows the signing secret. With `https://realgta.ca/webhooks/wave` Wave's validation failed every time with `Invalid webhook URL: Validation failed: [Errno 104] Connection reset by peer` -- the request never reached the Worker (`wrangler tail` empty) and no Cloudflare security event was logged for it; **cause not identified** (an earlier "Managed rules" block in Security > Events was an unrelated scan hours before, misattributed at first; a WAF skip rule for `/webhooks/wave` that the user added made no difference and is unnecessary). The workers.dev URL passed at once, so it is the registered one -- do not "fix" it back to realgta.ca. The endpoint answers `200 {ok:true,configured:false}` while no `WAVE_WEBHOOK_SECRET` is set (Wave checks for a success before it reveals the secret) and is strict (401 for anything unsigned) once the secret is set; `GET /webhooks/wave` = 200 reachability. The signing secret is shown in the Wave portal (Webhooks page > the app > Secret token) and must be stored with `wrangler secret put WAVE_WEBHOOK_SECRET` (piped from the clipboard so it never appears in chat). To debug a delivery: same page > "Logs & deliveries" tab, and our `wave_events` table.
